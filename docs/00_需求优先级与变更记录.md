## 3. 需要明确覆盖旧说法的条目
- “重构旧 travel-planner-v2 / 迁移旧表”不适用于本项目。旧稿只作需求历史。
- “最后才看真实 Provider 数据”不采用：先做契约验证/样本探针；不能到正式 UI 接入才发现没有需要的字段。正式集成按阶段、凭证、覆盖范围推进。
- “后台由服务器负责”不表示服务器能读取手机定位；客户端采集经授权的位置、上报时间/精度/能力状态，服务器只处理收到的证据。
- “先把所有未来表建出来”不采用；第一阶段只做必要骨架，未来能力保留边界/文档，不造空实现。
- “退款必须到账状态机”已取消；用户直接记负数，无复杂跟踪。
- “用户设置的所有时间绝不可自动变化”指独立意图/锁定/班次事实不能暗改；用户明确采用路线时，允许其所授权的派生时间联动。
- “无班次交通可自动更新”仅指**既有选择内、无语义变化的估算刷新**；不包括重新叫车、改路、改方式或产生新费用承诺。
- “风险高=交通立即删除”不成立；预计赶不上与已确认错过分开。
- 未知信息可以保留，不等于任何实时判断可继续输出正常。
- 起床/闹钟建议不在首轮；保留最晚离开时间的核心计算。
- 最终记录交通展示方式仍标为暂定；不得以其为由删除未执行交通历史、费用或附件。

## 4. 时间模型的必要澄清
用户把到达目标改成19:30而旧交通仍19:56到时，不存成一个“到达19:30却由19:56交通支持”的自洽正式结果。存储**新的要求**与**旧采用方案**，投影显示目标停留51分钟和当前方案停留25分钟（具体UI后置）。不把目标、预测和实际混为一列。

`必须值`、`建议值`必须绑定它们真正适用的位置/环节。到机场、过安检、停止检票不是同一参照。只有语义可比较时才显示正常/黄/红；这不是新增用户字段，是防止错误算术的内部契约。
