# 多方向排程与冲突求解｜执行基线 v0.3
**基于已确认v0.2和本轮案例；复杂推荐质量仍在迭代。以下样例不是已核验时刻表。**

## 1. 核心关系
Visit：arrival + dwell = departure。Transport：fromDeparture = routeStart，toArrival = routeEnd。均需引用具体位置/环节和完整日期时区。

同一引擎支持forward、backward、bidirectional、mixed；不是四套模式或四份状态。先确定哪一端/哪一段，就从已有锚点传播约束。

### 1.1 O-03 timeline、当地显示与 DST（产品规则已确认）

- 传播图与界面时间轴的真实先后必须建立在独立 sequence 上；已有明确 instant 时按 instant 判断
  时间先后。整趟旅行不得按 `localDate + localTime` 排序。
- `localDate` / `localTime` 是当地显示值。跨时区导致钟点或日期回拨时保留真实显示，不为了
  视觉递增改写时间；只在发生时区变化的 Transport 上解释时区切换，后续卡片不重复标注。
- 一条跨日 Transport 是一个计算与业务 subject；它在多个日期卡中显示时仍共用同一份
  PLANNED/ESTIMATED/ACTUAL、费用、状态与备注，不能因投影重复计算或产生多份事实。
- 跨国际日期线可让同一 `localDate` 在 sequence 中出现多次。每张日期卡有独立身份（架构概念
  `DayOccurrence`），传播和编辑必须引用具体 occurrence，不能仅凭日期值匹配或合并。
- 被连续 Transport 完整覆盖的中间自然日是“交通占用日”：日期卡和 DateOwnership 存在，
  但不能在其中插入普通 Place/FreeAction。最终存储/投影方案仍待 P3 前设计。
- 可靠 Provider/固定服务数据已有明确 instant 或 UTC offset 时直接使用，不询问用户选择。
- 用户手工输入 DST 回拨日重复出现的当地钟点时，必须选择前一个或后一个 occurrence；UI 可显示
  不同 offset 辅助理解，但不得默认选择。DST 跳时中不存在的钟点明确拒绝，不自动平移或静默
  接受。只有 local clock 且信息仍不足时返回 `AMBIGUOUS_TIME_INPUT` / `UNSUPPORTED_SCENARIO`。
- 上述产品判断已经确认；DayOccurrence/sequence migration、跨日投影和 DST command/UI 尚未实现。

## 2. 必须分开存储
| 概念 | 例子 | 处理 |
|---|---|---|
| 用户目标 | 浦东23:30前到 | 不被23:00路线结果覆盖 |
| 用户停留要求 | 南京南至少40分钟 | 到得早时可以实际留45分钟 |
| 当前采用结果 | 19:36到、20:21发车 | 计算45分钟，不伪造为19:41 |
| 预测 | 实时预计19:42到 | 不覆盖原定/实际 |
| 实际 | 真实确认19:38到 | 后续自动重排不能改写 |

## 3. 字段编辑如何决定方向
- 到达为独立输入、离开为派生：修改停留默认保持到达，推离开。
- 离开为独立输入/已选班次、到达为派生：修改停留默认保持离开，推到达目标。
- 两端均由已采用交通确定：停留是结果；用户改停留，形成新要求与当前方案冲突，不改班次。
- 有🔒先尊重锁；两个用户独立输入仍无法辨别保留方向，返回AMBIGUOUS_TIME_INPUT并只问必要的一项。
- 普通计划到达、最晚到达、精确到达不同；接口明确intent，不把所有输入自动解释为≤。
- 缺少变量允许留空；从一个时间不能虚构另两个。无起点到达/无终点离开无需补假值。

## 4. 三个基准案例
### C01 中间固定车次反推
固定列车20:21南京南出发、21:22虹桥到达。南京南预留20分钟 → 到站目标≤20:01。前段候选19:20出发/19:56到；采用后南京南当前计划停留25分钟。

### C02 增加最低停留
当前19:56到、20:21走；改为至少40分钟 → 目标≤19:41；旧方案冲突15分钟。旧交通不改，查询前段候选。采用19:36到的新方案 → 停留45分钟；仍保留最低40分钟要求。

### C03 直接编辑到达目标
用户设19:30到，20:21已固定 → 目标停留51分钟；旧采用方案仍是19:56到/25分钟并显示冲突。查询带明确到达语义；采用19:24到候选时，当前方案停留57分钟，但19:30目标继续保留。不能在正式结果里把19:30当19:56交通的到达事实。

## 5. 交通查询不是时间减法
Forward先求最早可出发；Backward先求最晚可到达；再查真实候选。固定发车不能跟着时间加减平移成不存在的班次。

先沿当前已选方案评估冲突；可为解冲突搜索替代，不以“最快20分钟”冒充用户已采用的40分钟方案。替代成本、风险、后续影响一起进入预览。

对已采用步行/驾车/出租车等，仅无选择改变的ETA刷新可自动进行。更换路径、交通类型、新增费用承诺必须用户采用；绝不自动下单。

## 6. 缓冲的参照和去重
必须值/建议值只用于其适用位置和截止环节；进站检票截止与到站提前量不可直接比较。缺少必要连接耗时就标UNKNOWN，不输出“安全”。

路线已包含站内步行则不重复加；station dwell包含步行+等待，不再额外加一次dwell。两端候车区间不是乘车时长。

浦东23:00到、次日02:00发：区间3小时；2.5小时是建议预留则已满足，不把航班改到01:30。

状态：达到可用建议为正常；低于建议/用户🔒但未突破必须为黄色；低于可靠必须值为红色。数据不够时UNKNOWN与三色并列，不把未知当正常。

用户接受风险只抑制同层重复提醒，不修改客观阈值。不能将红色方案标成“已解决”，仍可以用户明确接受保留。

## 7. 传播遇到边界
固定班次、用户独立约束、已发生事实都不能自动挪动，但可继续计算影响。未选边使依赖它的结果变未知，不抹掉其他锚点。两侧不可同时满足时返回冲突集，不循环覆盖两端直到看似收敛。

对每个可计算区间做上下界传播；约束不一致给出最小可解释冲突。算法必须有有界终止条件和循环检测；不以“反复加减直到误差很小”处理约束。

## 8. 冲突候选生成与排序
先评估局部交通替代能否保住现有安排。失败或不接受，再考虑前序压缩/提前、后续顺延、用户确认的预约调整、保留风险。每个候选包含：改哪些点/边、释放多少时间、增加费用（未知则未知）、影响哪些受保护安排、体验时长变化、依赖哪些未确认外部条件。

受保护安排只来自两类明确来源：系统已有的可靠结构化事实（例如已采用固定班次或结构化确认的
预约/门票时间），或用户主动标记“已预订 / 时间固定”。普通计划、备注里的“已订”、附件或模糊
文字都不能自动建立保护；V1 也不要求订单号、截图、付款凭证或 OCR。

冲突求解优先尝试保住受保护时间，但“保护”不是不可修改的绝对禁令。现实条件无法满足时，必须
展示冲突与影响，让用户决定是否调整；不能因为安排被标记保护就伪造一个可行解或“已经解决”。

默认展示1推荐+最多2个可靠备选，不要求凑满3个。若只有1或2个真实候选，就只给1或2个。没有可靠解时说没有可确认方案，并保留用户主动编辑入口。每个推荐必须说明关键取舍、依据和未知项。

约束：不动已执行部分、不假设餐厅18:00有位、不篡改班次。系统可建议用户自行联系调整预约；
用户完成外部操作并点击“已调整”后，可按用户确认的新时刻继续规划，不要求 API 回执、订单号、
截图或 OCR，也不建立复杂外部状态机。该状态只能表述为“用户确认已调整”，不能称为商家官方
确认或有位；用户后来发现失败时可再次调整。

推荐策略与纯传播分开。先过滤违反事实、受保护安排和用户硬约束的方案，再优先保护固定/受保护
内容，以最小改动为基线，并比较额外成本、剩余体验、时间收益、风险和影响范围。已知偏好可参与
可行候选排序，但不能覆盖事实或约束。**不硬编码全局评分权重，不把最便宜或最快设为永久优先，
不宣称最优。**

晚餐剩60分钟与20分钟是测试对照，不是全世界餐厅的质量阈值。没有用户要求/可靠依据，展示
“90→20分钟”的损失但不武断禁止；只有用户为该活动明确设置的最低体验时长才成为硬约束。
O-05/O-06 已解决产品判断；RecommendationPolicy 与真实外部 Provider 仍未实现。

## 9. 安静辅助
首次实质冲突可给方案。用户拒绝/关闭后进入quiet-assist：只更新缺口和状态，不重复主动推荐。用户要求或新事实导致风险明显升级才再生成。解决时状态静默消失。

同一个风险事件默认只主动提醒一次。时刻每过一分钟不视为“新的重大风险”；`8 → 7` 分钟通常
不是新事件，`8 → 1` 分钟或从“换乘较紧”升级为“很可能错过固定班次”可以成为新的严重等级。
不设“减少 X 分钟就提醒”的全局硬编码。

事件需有 stable event key、severity、basisVersion 和 acceptedAt。用户选择“知道了，继续按这个
计划”只接受当前等级，同等级保持安静，升级后仍可提醒；用户主动 snooze 到期且风险仍在，也可
再次提醒。解除风险时取消预约提醒任务。

实时计算可以提前静默运行，只在需要行动的窗口主动打扰。固定提醒与动态提醒目的相同时去重；
过期固定提醒不补发旧指令。多个提醒并发时优先明确时窗与严重后果，通知正文显示关键行动并将
低优先级项汇总为“还有 N 个待办”。

## 10. Preview / Adopt与撤销
计算、查询、预览可以自动；修改选择必须经采用。保存用户的新要求不等于自动采用为解决它而生成的路线。

Adopt基于版本、候选有效期、授权、幂等键原子提交。版本过期先重算，不把旧预览强行写进去。撤销用户动作与内部连带结果，但不能撤销之后发生的外部事实；按最新证据重算风险。

## 11. 可直接测试的状态与限制
- 计划=当前正式已采用输入，预计=最新可确认的计算，实际=已发生证据；互不覆盖。
- 计划编排可从中间开始；旅行正在执行时不允许反推改写已完成时间。
- 计划期结束后 Trip 可自然成为“已结束”，不以 Actual、定位或 App 使用记录为门槛，也不追问
  用户是否真的旅行；只有用户主动明确表示没去才是 `NOT_TAKEN`。
- 旅行执行中的当前当地时区依次来自可靠设备定位、设备当前时区、当前行程地点的已知时区
  上下文；不得使用服务器默认时区。时区/定位只提供时间上下文，不能据此生成 Visit 已完成、
  到达具体地点或 ACTUAL 时间。
- Query失败 / 无候选 / 确认停运必须不同结果。
- 缺少路径时不能把两项目标时间之差全部算自由空档。
- 不做AI推理必依赖：确定性规则和测试先行；未来推荐服务只能调用同一Preview/Adopt边界。
