3. 需要明确覆盖旧说法的条目

  • “重构旧 travel-planner-v2 / 迁移旧表”不适用于本项目。旧稿只作需求历史。
  • “最后才看真实 Provider 数据”不采用：先做契约验证/样本探针；不能到正式 UI 接入才发现没有需要的字段。正式集成按阶段、凭证、覆盖范围推进。

  • “先把所有未来表建出来”不采用；第一阶段只做必要骨架，未来能力保留边界/文档，不造空实现。
  • “退款必须到账状态机”已取消；用户直接记负数，无复杂跟踪。
  • “用户设置的所有时间绝不可自动变化”指独立意图/锁定/班次事实不能暗改；用户明确采用路线时，允许其所授权的派生时间联动。
  • “无班次交通可自动更新”仅指既有选择内、无语义变化的估算刷新；不包括重新叫车、改路、改方式或产生新费用承诺。
  • “风险高=交通立即删除”不成立；预计赶不上与已确认错过分开。
  • 未知信息可以保留，不等于任何实时判断可继续输出正常。
  • 起床/闹钟建议不在首轮；保留最晚离开时间的核心计算。
  • 最终记录交通展示方式仍标为暂定；不得以其为由删除未执行交通历史、费用或附件。

4. 时间模型的必要澄清

用户把到达目标改成19:30而旧交通仍19:56到时，不存成一个“到达19:30却由19:56交通支持”的自洽正式结果。存储新的要求与旧采用方案，投影显示目标停留51分钟和当前方案停留25分钟（具体UI后置）。不把目标、预测和实际混为一列。

必须值、建议值必须绑定它们真正适用的位置/环节。到机场、过安检、停止检票不是同一参照。只有语义可比较时才显示正常/黄/红；这不是新增用户字段，是防止错误算术的内部契约。

0. 产品宪法 / North Star

终极目标：基于用户自己的需求、偏好与约束，为用户规划一套对这个用户而言尽可能合适的旅程，并尽可能帮助用户把这套行程顺利落地；减少行前与旅行中的繁琐操作；旅行结束后留下真实、尽可能完整的旅行记录。

一句话愿景：

根据用户真正想要的旅行，帮他规划好、执行好、少操心，并留下真实而完整的旅行记录。

核心原则：

  • 计划服务于旅行，旅行不服务于计划；
  • 系统是助手，不是监督者；
  • 机械、可验证的工作尽量自动化，偏好与取舍由用户决定；
  • 用户偏离计划本身不是错误；
  • 重大变化优先最小改动；
  • 真实性优先于形式完整；
  • 不完整 ≠ 错误；
  • 没有可靠依据的信息不能编，估算必须标明；
  • 用户选择高风险方案可以继续，系统负责说明后果；
  • 产品逻辑先想完整，版本功能分阶段开放。

1. Trip 创建与基础属性

1.1 新建旅行最小字段

新建旅行只要求：

  • 旅行名称；
  • 开始日期；
  • 人数。

规则：

  • 开始日期必填；
  • 人数必填，默认可由界面给出合理值，用户最终确认；
  • 结束日期不要求填写，初始结束日期 = 开始日期；
  • 随 Day、跨日节点和实际行程自动扩展/收缩；
  • 目的地/国家/城市不是必填字段，由行程地点自动推导；
  • 旅行名称任何生命周期均可修改；
  • Trip 人数可修改，前期主要影响费用，不自动改地点/时间/交通。

1.2 Trip 级信息

保留：

  • 旅行总备注：可选纯文本，任何阶段可编辑；
  • 旅行总待办：标题、完成状态、备注、可选提醒时间；
  • 无提醒时间的总待办只在旅行总览展示，不主动通知；
  • 用户设定具体提醒时间后才通知。

1.3 用户级基准货币

  • 基准货币属于用户级全局偏好，不属于 Trip；
  • 与 UI 语言、目的地、系统地区解耦；英文界面也可以 CNY 为基准货币；
  • 用户修改基准货币后，所有旅行汇总视角同步切换；
  • 原始金额与原始币种永远不变。

2. Day、日期范围与 Trip 日期归属

2.1 Day 扩展

  • 新建后先有开始日期当天；
  • 通过「添加下一天」向后扩展；
  • 可以「添加前一天」向前扩展，不移动已有行程；
  • 可以在中间「插入一天」，插入点之后行程整体顺延，日期相关信息重新校验；
  • 可以「将后续行程整体提前一天」，当地钟点保持，日期相关信息重新校验；
  • Day 不作为普通可删除对象：头尾空白日自动收缩，中间空白日合法保留；新建空白Day的编辑保护与收缩时机尚待确认，不得创建后立即删除（O-01）。
  • 日期整体移动不能从跨日地点、自由行动或跨日交通中间切断连续关系。

2.2 修改出发日期

  • 旅行尚未开始执行时允许整趟改期；
  • 整体平移的是当地日历日期，不做 UTC 机械平移；
  • 各节点原当地计划钟点保留；
  • 具体班次、营业时间、季节运营等按新日期重新校验；
  • 进行中不能整趟改出发日期，只调整尚未发生部分；
  • 正常已结束旅行不能靠改日期重新激活，需要复制为新旅行。

2.3 日期唯一归属

核心规则：

同一个自然日，同一账户只能归属于一个 Trip。

补充：

  • 两趟旅行日期连续不代表自动属于同一 Trip；用户建立两个 Trip，默认就是两个；
  • 当某 Trip 扩展到已经归属于另一个 Trip 的日期时，不能先创建第二份同日期 Day；
  • 先提示日期冲突，用户可选择合并旅行，或先处理/释放原 Trip 的该日期；
  • “旅行日期区间重叠即禁止”的旧规则废弃，改为“自然日唯一归属 + 冲突解决”。

2.4 合并旅行

  • 日期冲突时可触发合并；无冲突时也允许用户主动合并；
  • 合并不要求日期连续，中间可形成合法空白日；
  • 合并是无损改变 Trip 归属，不是复制；
  • 两边已有地点、自由行动、交通、计划/预计/实际时间、执行事实、备注、待办、费用、附件等全部保留；
  • 已发生部分保持历史事实锁定；未来部分保持计划状态；
  • 如果前面已有实际发生内容、后面还有未来内容，即使中间为空白日，合并后的 Trip 整体仍可处于进行中；空白日不自动切断 Trip；
  • 合并时用户重新输入新的旅行名称；
  • 两边默认人数不同则由用户重新确认合并后 Trip 默认人数；
  • 两边总备注、总待办无损合并；
  • 合并后无法再拆分为原来的两趟，执行前必须明确提醒不可逆；
  • 不提供“拆分旅行”能力。

3. 地点、自由行动与相邻交通

3.1 地点

  • 空白日可添加第一个地点；搜索选中后立即加入，不强制先配完整时间；
  • 地点可插入或末尾追加；
  • 同一真实地点可重复出现，每次是独立 Visit；
  • 地点卡支持同日拖拽排序；只移动地点，不把原交通固定绑走；
  • 拖动完成后只重算发生邻接变化的边；
  • 删除地点不二次确认，提供短暂单步 Undo；
  • Replace 地点在原位置替换，旧相邻交通失效，新边待选择；旧备注不继承；
  • 地点名称/地址（身份）不直接编辑，要改变身份用 Replace。

3.2 自定义地点

  • 最小创建信息 = 名称 + 可定位的位置；
  • 有可靠地址则显示，没有正式地址但坐标可靠也允许创建；
  • 不为了完整性虚构地址；
  • 电话、分类、营业时间等不是必填。

3.3 自由行动

“自由行动”是特殊行程节点，不是假 Place：

  • 固定名称“自由行动”；
  • 无 Place ID/固定地点身份；
  • 支持计划/实际时间、备注、待办、费用、🔒、拖拽、删除、撤销；
  • 可首尾、可跨日；
  • 不因为定位或消费自动拆成地点；
  • 用户可事后转换为正式地点或拆为多个正式地点+交通；
  • 若两个自由行动因删除中间地点而相邻，不自动合并，轻提示用户决定；
  • meaningful gap（当前测试阈值约 30 分钟）可询问是否填入自由行动，但不自动填满。

4. 交通、采用与换乘节点

4.1 邻接交通

  • 当前有效时间轴只维护相邻行程节点之间的有效交通；
  • 插入/删除/拖拽只影响邻接变化的交通；
  • 旧失效交通进入历史，不参与当前排程；
  • 路线查询/预览绝不修改正式行程；点击 Adopt 后才落地。

4.2 多段交通展开

若 A→D 方案实际为 A→公交→B→火车→C→公交→D，采用后主时间轴展开为 A→B→C→D。

  • 真正上下车/换乘/等待的节点可成为正式交通生成节点；
  • 单纯途经站不展开；
  • 步行是交通段；
  • 同站内部换乘只保留一个站点卡，内部停留包含下车、站内步行、找站台、等待；
  • 用户计划地点与交通生成地点底层来源必须区分；
  • 重规划可替换交通生成节点，但不能静默跳过用户计划地点。

4.3 固定班次是事实型时间锚点

  • 已采用的具体火车、航班、巴士等班次，其出发/到达时刻天然成为事实型锚点；
  • 用户不需要再手动🔒一次；
  • 要改变该时间，需要换班次/换交通，不能直接把班次时间改成任意数字。

5. 时间模型与多方向排程

5.1 三层时间

Planned / Estimated / Actual 三层互不覆盖：

  • Planned：正式计划；
  • Estimated：当前动态预计；
  • Actual：真实事实。

5.2 地点三变量

普通地点核心关系：

到达时间 + 停留时长 = 离开时间

任意两个可推第三个：

  • 到达 + 离开 → 停留；
  • 到达 + 停留 → 离开；
  • 离开 + 停留 → 到达。

但必须同时记录每个值的来源/语义，至少能区分：

  • 用户正式计划值；
  • 用户约束/目标；
  • 已采用交通推导结果；
  • 系统建议；
  • Estimated；
  • Actual。

5.3 目标 vs 当前方案结果

例如：

  • 用户要求“23:30 前到浦东机场”；
  • 当前选定路线实际预计“23:00 到”。

二者必须同时保留：

  • 23:30 是用户条件；
  • 23:00 是当前方案结果；
  • 后续方案变成 23:10 仍可能满足原目标；
  • 不能用方案结果覆盖用户条件。

同理：

  • 用户希望南京南至少预留 20 分钟；
  • 当前交通算出实际停留 25 分钟；
  • 20 分钟继续作为要求，25 分钟是方案结果。

5.4 从任意方向推导

同一套引擎必须支持：

  • 从头向后推；
  • 从尾向前反推；
  • 从中间锚点同时向前/向后推；
  • 在同一规划过程中随时换方向，不需要切换“模式”。

真实交通不是纯算术：

  • 先计算查询条件（如最晚到站、最早出发）；
  • 再查询真实路线/班次；
  • 用户采用后，真实交通结果回填相邻地点时间；
  • 到得比目标更早，显示真实时间，不为了凑目标伪造时间。

5.5 修改时间后的自动化

例：南京南当前 19:56 到，G93 20:21 出发，停留25分钟；用户把到达时间改成19:30。

  • 20:21 班次事实保持；
  • 停留自动重算为51分钟；
  • 原前段交通若仍19:56到，则与新计划19:30冲突；
  • 系统自动以“到达南京南 ≤ 19:30”为条件重新查询前段交通；
  • 无班次交通仅可在既有选择不变且无歧义时刷新估算；新路线、方式变化或新的费用选择仍需采用，不自动订车。
  • 有具体路线/班次选择的交通，系统自动查询、推荐，但用户确认 Adopt 后才替换。

6. 🔒、客观约束、缓冲与风险

6.1 约束优先层

当前原则：

客观规则/事实 > 用户明确保护的约束 🔒 > 用户正式计划值 > 尚未采用的系统建议

说明：用户仍可选择冒险，但系统不能把客观事实降级为不存在。

6.2 🔒 的用途

🔒用于用户自己的重要意图：

  • 固定时间；
  • 最早/最晚；
  • 最低停留；
  • 个人预留；
  • 重要偏好。

固定班次本身不需要再🔒。

6.3 缓冲

不做全球统一“火车20分钟、航班2小时”的死表。按具体场景维护：

  • mandatory：客观必须值；
  • recommended：更稳妥建议值；
  • 用户自己的预留要求。

如果只有 mandatory：正常/红；只有 recommended：正常/黄；缺依据不制造红线。

不同安排约束语义不同：

  • 火车/航班/末班车等不等人，客观截止更硬；
  • 餐厅预约可能有迟到容忍，但没有可靠规则时不能瞎猜；
  • 没有明确硬规则时，把“时间非常紧张”交给用户判断，用户可保持不改；
  • 用户已接受同一层级风险后不重复催，除非风险升级/事实变化。

7. 冲突求解与方案推荐（持续迭代模块）

7.1 核心目标

系统不能只报“还差20分钟”，而应该主动把可行妥协算出来。

系统负责算时间账和后果，用户负责选择自己愿意接受的妥协。

7.2 最小改动优先

当中间停留延长导致后续冲突：

  1. 先检查能否只改局部交通解决；
  2. 若可行，给出时间收益、额外费用、风险；
  3. 用户接受 → 只改这一段；
  4. 用户拒绝/代价不可接受 → 再向前或向后传播调整；
  5. 后续预约/活动本身可调整时，也可成为候选解，但要计算对更后面时间轴和体验的影响。

例：美术馆17:10离开、餐厅17:30预约；巴士40分钟，打车20分钟但贵很多：

  • 优先可以提示“换打车即可保住当前美术馆停留和17:30预约，预计增加费用800”；
  • 用户接受则局部解决；
  • 不接受再考虑提前前段到达、压缩地点、修改预约等。

7.3 方案不能只看可行性，还要看质量

例如把餐厅改到18:00：

  • 若还能吃约60分钟，可能是合理妥协；
  • 若只能吃20分钟，即使数学上赶得上后续演出，也可能体验明显过差；
  • 方案推荐必须评估“剩余体验”，而不是只求时间可行。

7.4 推荐排序

已知用户偏好时，允许基于偏好标出“更适合你的方案”，但不自动采用。 未知偏好时默认：

  1. 保住重要/受保护安排；
  2. 风险更低；
  3. 影响范围更小；
  4. 再综合费用、时间与体验质量。

不能把“最便宜”或“最快”天然当成最优。

7.5 方案展示数量与打扰尺度

  • 默认 1 个主推荐 + 最多2个备选；
  • 都不接受，用户可自行调整；
  • 用户拒绝/关闭推荐面板后，同一风险进入安静辅助：只实时更新剩余缺口和风险，不再主动弹新方案；
  • 用户主动“帮我优化”才重新生成方案；
  • 同一冲突解决后，风险标识静默消失，不弹“优化成功”；
  • 风险明显升级/事实变化 = 新风险事件，可重新提醒，并必须基于新现实生成新方案。

7.6 Preview / Adopt

所有涉及：

  • 换具体交通；
  • 增加显著费用；
  • 改预约；
  • 改重要行程； 都必须 Preview → 用户确认 → Adopt。

计算可以自动、查询可以自动、推荐可以自动，但决策不能被系统静默采用。

8. 执行生命周期与实时监控

8.1 Trip 生命周期

  • 到达旅行开始日期后，系统默认 Trip 已进入进行中；
  • “进行中”不等于从00:00开始持续定位；
  • 用户晚出发、睡过头、第一天被打乱，仍属于进行中的意外情况；
  • 系统不能仅因未检测到执行证据就自动判“未执行”；
  • “未执行”必须由用户确认；
  • 计划周期结束但最终结果不明时，进入内部“待确认”状态，停止实时监控，不自动判完成/未执行；
  • 用户下次进入时确认“实际发生了 / 没有去”；
  • 发生了 → 历史整理，未知事实保持未知；
  • 没有去 → 未执行计划。

8.2 正常结束与异常收尾

  • 最终终点实际到达确认 → 自动进入历史旅行；
  • 有可靠证据证明曾实际执行、但未正常确认终点且计划期结束 → 可结束为记录不完整；若连是否发生也无法确认，则进入待确认，不自动归为未执行。边界验收见未决项。
  • 只有“自动异常收尾、记录不完整”的旅行允许恢复为进行中；
  • 正常已结束旅行不可通过改日期重新激活。

8.3 实时监控启动

状态和监控分离：

  • Trip 可以已经进行中，但实时监控尚未启动；
  • 用户当天主动打开旅行 → 可启动监控；
  • 当天第一个有明确计划时间且值得监控的节点进入临近窗口 → 可启动；
  • 无明确时间 + 用户未打开 App → 不主动全天监控。

8.4 监控持续与停止

  • 一旦启动，可在锁屏/退出 App 后后台继续；
  • 只有仍有实时执行价值时持续；
  • 无剩余实时判断价值时自动停止，即使最后事实未确认也可留下未知；
  • 跨日交通/地点/自由行动有执行价值时可跨0点继续；
  • 用户可主动“停止实时监控”，只关闭实时执行层，不结束旅行；
  • 用户主动停止后跨天保持关闭，直到用户主动重新开启；
  • 系统自然停止后，后续满足条件可自动恢复；
  • 普通用户定时提醒不受“停止实时监控”影响；
  • 用户主动停止实时监控后，位置、实时交通刷新、动态ETA、最新出发时间、自动到达判断、风险计算等都暂停。

8.5 定位/后台能力失效

  • 定位权限失效 ≠ 用户主动停止监控；
  • 实时层仍开启，只暂停位置依赖能力；权限恢复自动恢复；
  • 后台被系统暂停/杀进程后，恢复时重新同步当前时间、位置、交通状态；
  • 中断期间未知事实保持未知，不续算旧ETA、不补造轨迹；必要时提示一次“实时监控曾中断，已重新同步”。

9. 实际执行、延误与重规划

  • Actual 已发生部分锁定，未来重规划不能改写过去；
  • 偏离本身不是风险，影响受保护安排才形成风险；
  • 延误不默认整天整体后移，先看当前缓冲/停留能否吸收；
  • 一个地点可吸收时可建议具体缩短值；多个地点需释放时间时，系统应算出少量可行妥协方案，不把算术丢给用户；
  • 用户可以拒绝所有方案自行调整；
  • 错过具体服务后同时比较下一班/替代交通，Preview 后 Adopt；
  • 当前实际位置作为重规划起点；若实际位置成为执行事实，可进入最终记录；
  • 用户计划地点不能静默跳过，交通生成节点可随新路线替换。

提醒：

  • 延误/明显偏离先一次聚合提醒；
  • 每个受保护安排临界点可再提醒一次；
  • 同一风险用户忽略/拒绝后不重复催；
  • 风险升级、事实变化、新受保护安排受威胁 = 新风险事件；
  • 普通提醒 App 内；关键风险/需决策可系统通知 + App 内。

10. 跨日与时间显示

10.1 跨日关系

相邻 Day 可合法存在：

  1. 同地点连续；
  2. 交通本身跨日；
  3. 用户接受未连接。
  • 跨日地点/自由行动是同一连续节点，不拆成两份；
  • 跨日交通按出发日→到达日连续记录；
  • 不为了公式完整制造假节点/假时间。

10.2 时区

  • 没有 Trip 级统一时区；
  • 每个地点/事件按事件所在地当地时间展示；
  • 底层保留时区与UTC；
  • 跨时区航班轻提示“出发/到达均为当地时间”；其他普通行程不重复提示。

11. 待办、附件、备注

11.1 待办

用户侧刻意做轻：

  • 标题；
  • 未完成/已完成；
  • 备注；
  • 可选提醒时间。

日级待办：每天第一次打开该旅行时集中展示当天相关待办一次；当天不反复弹；未完成不自动滚到下一天。

Trip 总待办：无明确提醒时间仅在总览展示。

11.2 附件

  • 可挂地点、交通、Trip；
  • 单附件一个主要归属；
  • 图片/PDF/常见文档；
  • 当前只做存储/查看/下载/删除；
  • 不默认OCR/AI解析/二维码识别；未来只有用户明确触发才解析。

12. 费用 / 记账

12.1 定位

行程是主线，记账是辅助；不记费用不影响行程成立。

12.2 原始记录与汇总

  • 原始金额/币种永久保留；
  • 实际费用按消费发生日历史汇率快照换算；
  • 用户切换基准货币后，历史旅行汇总按发生日历史汇率关系切换到新基准币，不用今天汇率重算过去消费；
  • 没有可靠历史汇率就待换算，不编造。

12.3 计划费用 / 实际费用

  • 两层都可选；
  • 计划费用可按人计价或整笔计价；
  • Trip 人数是默认人数，单笔计划费用可覆盖人数；
  • 只有继承 Trip 默认人数的计划费用随 Trip 人数变化；
  • 实际费用记录真实总金额，一旦发生不再随人数变化；
  • 实际支付可由计划费用预填，但用户以真实付款修改；
  • 退款/补差/手续费用正负新记录追加，不覆盖原记录。

12.4 汇总

  • 当天只显示计划总数、实际总数；
  • 整趟显示 Plan Total vs Actual Spent，并可看分类；
  • 不做“当前预计总花费”；
  • 预算系统暂缓。

13. 历史回顾与分享

13.1 历史回顾

旅行结束后自动形成回顾视图，不要求用户额外生成或查看。

回顾默认极简：

  • 日期；
  • 可可靠识别的城市/区域；
  • 当天实际去过的地点；
  • 自由行动；
  • 按实际发生顺序；
  • 同一地点去两次保留两次；
  • 跳过/未确认默认不展示；
  • 不默认展示交通、交通时长、风险历史、计划vs实际等执行细节。

回顾页默认只读；修改事实进入单独“整理/编辑实际行程”状态。历史编辑不重新启动实时执行。

13.2 一键分享图片

用途：给人看。

  • 一键生成整趟旅行一张长图；
  • 顶部旅行标题；
  • 按日期/城市区域展示极简地点主线；
  • 旅行前/进行中：取当前有效计划；
  • 旅行结束后：取最终实际去过的主线；
  • 不含交通、费用、执行状态；
  • 即时生成，不保存分享历史。

13.3 行程分享链接

用途：给别人拿去用。

  • 分享的是可复用行程骨架，不是展示网页；
  • 一次性领取链接；
  • 打开预览不消耗；成功复制到接收者账户后链接失效；
  • 7天未领取自动过期；
  • 不绑定指定接收人，第一个成功领取者获得；
  • 每次点击分享生成新的独立链接；
  • 原作者不需要分享状态管理/领取者/查看次数；
  • 可匿名预览，复制时登录；
  • 分享链接是静态快照，与原旅行后续编辑不联动。

复制范围：

  • 地点卡片；
  • 自由行动；
  • 计划时间；
  • 参考交通（类型、班次/线路、上下车与换乘路径、参考时间、用时）；
  • 参考交通复制后必须按接收者新日期重新校验，不能直接视为有效；
  • 不复制票价；
  • 不复制任务、总待办、备注、总备注、费用、附件、订单/预约事实、实际执行状态、历史记录。

复制流程：

  • 预览以 Day 1～Day N 为核心，不突出原作者绝对日期；
  • 点击复制 → 选择新出发日期 + 确认/修改人数 + 确认/修改名称 → 创建 → 直接进入编辑页；
  • 名称默认“原名称 copy”，重复复制为“copy 2 / copy 3 …”；
  • 日期平移保留当地计划钟点；
  • 日期相关客观事实重新校验；
  • 中间空白 Day、跨日结构保留；
  • 局部交通查不到或地点失效不阻止复制，标记待处理/已失效；
  • 原行程不完整也可分享。

旅行结束后分享/复制：

  • 取最终实际执行形成的骨架；
  • 实际时间作为新计划参考；
  • 实际时间缺失就留空，不拿旧计划冒充；
  • 实际交通确认过则保留为参考交通，未知则留空；
  • 交通生成换乘节点作为参考交通路径信息，不锁死为接收者正式旅行目的地。

自己“历史旅行复制为新旅行”与别人领取分享链接共用同一底层复制能力。

14. 网络、数据可靠性、保存与多设备

14.1 网络与供应商

  • 无网络：产品采取硬失效态，不把旧缓存伪装成当前可靠界面；
  • 网络恢复后先重同步关键数据再恢复正常界面；
  • 单一供应商失败：只让对应能力失效，不让全App失效；
  • 已确认计划事实可以显示，实时状态明确“当前未知”；
  • 可靠备份供应商可自动接管，但不能为了有结果而降质量；
  • 多个可靠来源冲突不做平均，按预设主来源并暴露冲突。

14.2 自动保存

  • 普通编辑自动保存，无常驻 Save；
  • 显示 Saving / Saved；
  • 持续失败明确 unsynced，不假装已保存；
  • 自动重试少量次数；
  • 离开时若仍有未保存失败编辑，提示重试/放弃；
  • 多设备用乐观版本，不做 silent last-write-wins；
  • 冲突时保留本地未同步编辑但不自动提交/合并。

14.3 Undo

  • 重要编辑支持短时单步 Undo；
  • 一个业务动作及其自动副作用作为一个原子动作一起撤销；
  • 只保留最近一次，不做复杂历史。

15. 当前开发策略

现在已经具备进入 Backend Domain Blueprint 和领域引擎开发的条件。

建议顺序：

  1. Domain model / 状态机 / 时间与约束模型；
  2. 多方向排程引擎；
  3. 冲突检测与 explainable reason/source；
  4. Preview / Adopt 事务边界；
  5. 自动化测试；
  6. 薄测试 UI；
  7. 正式 Desktop / Mobile UI 后置。

必须保证：

  • 计算与采用彻底分开；
  • 每个推导结果最好带 reason/source，能解释“为什么是这个时间/为什么冲突”；
  • 冲突求解推荐策略独立成可替换/可迭代策略层，不写死进核心时间传播；
  • 后续新增案例优先变成自动化测试。

16. 仍在持续讨论 / 不应写死的部分

主要开放项集中在“冲突求解推荐策略”：

  • 体验质量如何量化/分级；
  • 成本、时间、影响范围、风险、偏好的综合排序；
  • 不同预约类型的可调整性与外部变更能力；
  • 推荐解数量、解释语言、触发时机的 UX 细化；
  • 更多真实案例验证。

这些不阻止领域底座开始开发，但必须设计成可演进规则，而不是散落硬编码。

17. 已废弃 / 被替换的旧规则

以下不再作为开发依据：

  • “整个日期区间不允许重叠，一碰到别的Trip就禁止” → 改为自然日唯一归属 + 合并/释放冲突；
  • “日期全部过去后自动判未执行” → 未执行只能由用户确认；
  • “必须有可靠执行证据才进入进行中” → 到开始日期默认进入进行中，监控另行启动；
  • “当天执行开始 = 第一个地点离开时间” → 生命周期与实时监控拆开；
  • “创建旅行必须填结束日期” → 只填开始日期，结束日期由行程推导；
  • “无具体日期也可以先做 Day1～DayN 规划” → 创建必须有开始日期；
  • “自定义地点必须有规范地址” → 名称 + 可定位位置即可；
  • “交通生成节点分享时完全不复制” → 作为参考交通路径信息保留，但不锁死为正式地点；
  • “分享都是链接/分享都是展示” → 一键分享图片给人看；行程分享链接给别人用；
  • “行程分享长期链接” → 一次性领取链接，7天过期；
  • “行程分享复制任务/可复用任务” → 不复制任务/备注等，只复制行程骨架；
  • “历史旅行通过改日期重新用” → 复制为新旅行；
  • “拆分旅行” → 取消；
  • “地点时间以开始+停留为唯一主要输入” → 到达/停留/离开三变量任意两个推第三个；
  • “固定班次也需要用户手动锁时间” → 已采用固定班次天然为事实型时间锚点；
  • “多个地点可压缩时只告诉用户缺多少时间” → 系统应生成少量具体可行妥协方案，用户选择；
  • “用户拒绝推荐后继续动态弹新方案” → 用户拒绝/关闭后进入安静辅助，仅风险升级时重新提醒。

  • 后端领域优先，正式客户端后置；仅做必要的薄测试界面验证，不同时开发六个端。
  • 多用户与数据隔离从首轮开始；管理员邀请开通，首版无公开注册。
  • 首版无协作；预留集中授权边界，不提前做成员/共同编辑/共享位置系统。
  • 同一账号可多设备登录，修改走服务端版本校验，不做最后写入覆盖。

  • 每阶段功能分支、测试、commit、push、PR；检查后经用户同意再合并main。
  • 每次开发要求必须明确推荐模型与推理强度；选择须随任务难度和实际可用模型更新。

20. 仍保留在完整蓝图的细则（不因首轮后置而丢失）

费用与人数

  • 用户手工记账核心只有名称、金额、币种；不增加强制分类/备注/付款人表单。
  • 日期默认来自当前记录上下文，补录以用户填写的消费/服务归属日期为准；支付日期和录入日期不覆盖行程归属日期。
  • 具体节点关联只推荐，用户确认；不选就先按天，不强制挂地点。
  • 用户主动选择币种永远优先；所在地仅用于预选，不按界面语言强行改变。跨国票据有明确计价币种时按该币种。
  • 分类少而稳定：交通、住宿、餐饮、门票/活动、购物、其他；当天不做分类展开，整趟可看分类。
  • 计划/实际分开，未实际记账不把预计当已花；实际与某计划费用的对应只推荐，由用户确认。
  • 计划费用跟当前有效行程，失效预计退出当前计划合计；实际已花不因地点/交通删除而消失。删除归属节点时保留实际费用及必要说明，不级联删除真实支出。
  • 退款直接负数记录，不维护到账状态；补差/手续费追加；用户可随时纠正或删除错误账目。
  • 跨多晚酒店费用底层一笔，日汇总按已确认服务周期展示性分摊；计划按计划周期、实际按实际周期。跨日交通整笔归出发日。
  • 按人计划费用可用Trip默认人数或单笔覆盖；人数变化不能改历史实际总金额。
  • 预算、多人分摊、OCR小票识别留未来，不进入首轮。

记录与附件

  • 最终一条时间轴保留地点执行状态（已执行/已跳过/未确认）；删除是编辑移除，跳过是执行结果，不混用。
  • 未执行的原交通不占默认最终主线；实际交通未知显示未记录。此展示方式暂定，原交通仍可留后台历史。
  • 自由行动的消费/备注不使其自动变成POI；只有用户主动转换，才变成普通地点或细化多个节点。
  • 节点上的备注/待办/附件在记录整理阶段仍可编辑；旅行级附件可放签证/保险等，单附件一个主要归属，不做文件夹网盘。
  • 所有附件有类型/数量/大小限制，具体数字后续工程阶段确定；默认不解析内容。
  • 旅行回顾只按日期、可靠区域和已执行地点/自由行动排序，重复到访不去重；交通、金额、状态等不默认出现在极简回顾。

分享与删除

  • 图片即时生成整趟长图，带标题；不带费用/私有附件，不存图片分享历史。
  • 行程分享是静态可领取骨架：匿名预览，登录后复制；有效7天，成功复制才消耗，不以预览/邮件扫描消耗。
  • 领取成功和新Trip创建需原子事务；创建因日期归属冲突失败不得消耗链接。每次生成独立链接，不做分享管理列表。
  • 自定义地点按普通地点一起复制，不另加用户已拒绝的隐私弹窗；系统仍限制分享范围，不把私有附件/备注带出。
  • 复制时保留参考交通类型/班次/路径/用时，但不复制票价；原车站只随参考路径保留，新路线确认后再展开，不把过时换乘点强制设必经。
  • 新日期若能证明实质同方案，可自动验证；发生实质选择变化仍须采用。局部验证失败不阻止复制，不伪造有效性。
  • Trip永久删除前强警告，不输入名称二次验证；删除数据并使尚未领取链接失效，别人的独立副本不受影响。
  • 不可逆合并不得伪装可Undo；无损合并保留来源、备注/任务/费用/附件，人数差异先由用户选默认人数。

这些规则分别纳入后续模块任务，不代表P0～P5自动授权开发全部功能。

每阶段独立分支和PR。P0完成停住；未获确认不能自动执行P1。 P2之后的详细任务在前一阶段真实代码基础上复核再发，不照纸面臆测路径。

3. 数据归属与权限

所有私有资源必须通过owner和所属Trip检查权限。owner从服务端会话取得，不信任客户端传来的ownerId。管理员仅能开通/禁用/撤销账号会话，不继承读取他人Trip、附件、位置、费用的权限。[S07]

首版一趟Trip一个owner；预留authorize(actor, action, resource)集中入口。不要提前建复杂协作表、共享定位或多人账本。

同一Place可有多个Visit；来源为USER_PLANNED / ROUTE_GENERATED / EXECUTION_ADDED，但三者可表现为普通地点卡。FREE_ACTION没有假Place/假坐标。

4. 时间不能仅有startTime/endTime两列

至少区分：

  • 输入意图：用户想要的目标时间/停留要求，包含比较运算EQ/NOT_AFTER/NOT_BEFORE/AT_LEAST与是否🔒。
  • 已采用的计划结果：路线和独立计划值支持的排程快照。
  • 当前预测：基于最新证据的预计结果，可失效。
  • 实际记录：已确认发生的事实，自动排程不能回写过去。

TimeValue建议包含：localDateTime、timeZone（IANA）、可确定时的instant、sourceKind、sourceRef、observedAt、quality。用户地点当地时间优先展示；持续时长用真实时间点之差计算。不使用服务器默认时区解析输入。

没有Trip级统一时区；生命周期日期的调度基准不能暗用服务器UTC，参见O-03。对夏令时重复/不存在钟点、跨日期线不确定归属，返回明确歧义，而不是自动纠正成看似有效的时间。

5. 一个节点，不复制跨日实体

跨日Visit或Transport是同一实体，在覆盖的Day里投影显示。费用不因重复显示而重复计数。跨日交通由真实出发/到达事实判断，不让用户手动给普通卡贴跨日标签。

不要只比较终点本地日期是否“大于”起点本地日期来推时长；跨时区航班可能本地到达钟点看起来更早。首轮先完成同一时区跨午夜与UTC时长测试；跨日期线Day投影待O-03。

6. 行程状态与监控状态分开

Trip生命周期提案：PLANNED、IN_PROGRESS、AWAITING_OUTCOME、FINISHED、NOT_TAKEN。FINISHED另带finishReason NORMAL/INCOMPLETE，不把不完整伪装成未去。

  • 到起始日期进入IN_PROGRESS是运行假设，不自动生成Actual事实。
  • NOT_TAKEN只能由用户确认；无数据不等于没旅行。
  • 无法确认整趟是否发生，计划周期后AWAITING_OUTCOME并停止任务。
  • 已有实际执行但尾段未知，可异常收尾；有争议按O-07不自动归类。

监控用户开关与当前运行状态也分开：userEnabled + OFF/IDLE/RUNNING/LIMITED。用户关掉后不因第二天或重新打开界面自动恢复；系统自然停止不改变userEnabled。

设备证据必须有deviceId、capturedAt、accuracy、source、receivedAt；晚到数据不能覆盖较新证据。位置输入只认用户授权客户端/主动填写，不通过服务器猜测。

7. Query / Preview / Adopt的事务规则

Query：传起終点、最早出发/最晚到达、日期时区、已有方案参考；返回候选与来源/有效期。不得写当前Trip。

Preview：以baseTripVersion、用户动作、provider snapshot和policyVersion计算变更。可保存临时候选，但不得修改正式节点/交通/通知。

Adopt：服务端重新校验权限、Trip版本、预览过期和Provider适用性；有效则一次事务落地节点、交通、来源与相关结果，并产生outbox事件。

必须有requestId/idempotencyKey；同一请求重试不能重复插入Visit、费用、任务或通知。相同key不同payload要拒绝。两设备同时采用同一baseVersion最多一个成功；另一个明确VERSION_CONFLICT。[S09]

一次采用失败不能只写了一半路线。外部API调用不要包在长数据库事务中：先取候选，事务提交时核验版本/快照有效性；必要时返回PREVIEW_STALE。

8. 撤销不是把世界倒回过去

单步、短时撤销恢复上一用户操作及其内部连带数据；不得回滚后续真实航班更新、实际位置或已发生事实。

若自上次操作后Trip版本已被其他设备修改，撤销返回UNDO_CONFLICT，不覆盖新改动。撤销成功后按最新可靠证据重新计算风险，不能恢复一个已经失真的“正常”状态。

Trip永久删除与不可逆合并不享有普通Undo；须用其已确认强提示流程。

10. 统一错误与解释结果

错误建议包含code、面向用户的中文message、requestId、retryable、必要的非敏感详情。示例： UNAUTHENTICATED / FORBIDDEN / VERSION_CONFLICT / PREVIEW_STALE / DATE_OWNED / PROVIDER_UNAVAILABLE / NO_MATCHING_CANDIDATE / LOCATION_UNKNOWN / CONSTRAINT_CONFLICT / AMBIGUOUS_TIME_INPUT / UNSUPPORTED_SCENARIO。

多方向排程与冲突求解｜执行基线 v0.3

基于已确认v0.2和本轮案例；复杂推荐质量仍在迭代。以下样例不是已核验时刻表。

1. 核心关系

Visit：arrival + dwell = departure。Transport：fromDeparture = routeStart，toArrival = routeEnd。均需引用具体位置/环节和完整日期时区。

同一引擎支持forward、backward、bidirectional、mixed；不是四套模式或四份状态。先确定哪一端/哪一段，就从已有锚点传播约束。

2. 必须分开存储

概念 例子 处理
用户目标 浦东23:30前到 不被23:00路线结果覆盖
用户停留要求 南京南至少40分钟 到得早时可以实际留45分钟
当前采用结果 19:36到、20:21发车 计算45分钟，不伪造为19:41
预测 实时预计19:42到 不覆盖原定/实际
实际 真实确认19:38到 后续自动重排不能改写

3. 字段编辑如何决定方向

  • 到达为独立输入、离开为派生：修改停留默认保持到达，推离开。
  • 离开为独立输入/已选班次、到达为派生：修改停留默认保持离开，推到达目标。
  • 两端均由已采用交通确定：停留是结果；用户改停留，形成新要求与当前方案冲突，不改班次。
  • 有🔒先尊重锁；两个用户独立输入仍无法辨别保留方向，返回AMBIGUOUS_TIME_INPUT并只问必要的一项。
  • 普通计划到达、最晚到达、精确到达不同；接口明确intent，不把所有输入自动解释为≤。
  • 缺少变量允许留空；从一个时间不能虚构另两个。无起点到达/无终点离开无需补假值。

4. 三个基准案例

C01 中间固定车次反推

固定列车20:21南京南出发、21:22虹桥到达。南京南预留20分钟 → 到站目标≤20:01。前段候选19:20出发/19:56到；采用后南京南当前计划停留25分钟。

C02 增加最低停留

当前19:56到、20:21走；改为至少40分钟 → 目标≤19:41；旧方案冲突15分钟。旧交通不改，查询前段候选。采用19:36到的新方案 → 停留45分钟；仍保留最低40分钟要求。

C03 直接编辑到达目标

用户设19:30到，20:21已固定 → 目标停留51分钟；旧采用方案仍是19:56到/25分钟并显示冲突。查询带明确到达语义；采用19:24到候选时，当前方案停留57分钟，但19:30目标继续保留。不能在正式结果里把19:30当19:56交通的到达事实。

5. 交通查询不是时间减法

Forward先求最早可出发；Backward先求最晚可到达；再查真实候选。固定发车不能跟着时间加减平移成不存在的班次。

先沿当前已选方案评估冲突；可为解冲突搜索替代，不以“最快20分钟”冒充用户已采用的40分钟方案。替代成本、风险、后续影响一起进入预览。

对已采用步行/驾车/出租车等，仅无选择改变的ETA刷新可自动进行。更换路径、交通类型、新增费用承诺必须用户采用；绝不自动下单。

6. 缓冲的参照和去重

必须值/建议值只用于其适用位置和截止环节；进站检票截止与到站提前量不可直接比较。缺少必要连接耗时就标UNKNOWN，不输出“安全”。

路线已包含站内步行则不重复加；station dwell包含步行+等待，不再额外加一次dwell。两端候车区间不是乘车时长。

浦东23:00到、次日02:00发：区间3小时；2.5小时是建议预留则已满足，不把航班改到01:30。

状态：达到可用建议为正常；低于建议/用户🔒但未突破必须为黄色；低于可靠必须值为红色。数据不够时UNKNOWN与三色并列，不把未知当正常。

用户接受风险只抑制同层重复提醒，不修改客观阈值。不能将红色方案标成“已解决”，仍可以用户明确接受保留。

7. 传播遇到边界

固定班次、用户独立约束、已发生事实都不能自动挪动，但可继续计算影响。未选边使依赖它的结果变未知，不抹掉其他锚点。两侧不可同时满足时返回冲突集，不循环覆盖两端直到看似收敛。

对每个可计算区间做上下界传播；约束不一致给出最小可解释冲突。算法必须有有界终止条件和循环检测；不以“反复加减直到误差很小”处理约束。

8. 冲突候选生成与排序

先评估局部交通替代能否保住现有安排。失败或不接受，再考虑前序压缩/提前、后续顺延、用户确认的预约调整、保留风险。每个候选包含：改哪些点/边、释放多少时间、增加费用（未知则未知）、影响哪些受保护安排、体验时长变化、依赖哪些未确认外部条件。

默认展示1推荐+最多2备选，不要求凑满3个。若只有2个真实候选，就只给2个。没有可靠解时说没有可确认方案，并保留用户主动编辑入口。

约束：不动已执行部分、不假设餐厅18:00有位、不篡改班次。调预约只能标为“需先联系确认”；在没有外部确认前不能标可执行新预约。

推荐策略与纯传播分开。已知偏好可参与排序；未知偏好参考受保护安排、风险、改动范围、额外成本和体验影响。不硬编码全局评分权重，不宣称最优。

晚餐剩60分钟与20分钟是测试对照，不是全世界餐厅的质量阈值。没有用户要求/可靠依据，展示“90→20分钟”的损失，不武断禁止；策略细化继续讨论。

9. 安静辅助

首次实质冲突可给方案。用户拒绝/关闭后进入quiet-assist：只更新缺口和状态，不重复主动推荐。用户要求或新事实导致风险明显升级才再生成。解决时状态静默消失。

时刻每过一分钟不视为“新的重大风险”。事件需有stable event key、severity、basisVersion和acceptedAt；防止重复发通知。15分钟再提醒是用户主动触发，解除风险取消预约提醒任务。

10. Preview / Adopt与撤销

计算、查询、预览可以自动；修改选择必须经采用。保存用户的新要求不等于自动采用为解决它而生成的路线。

Adopt基于版本、候选有效期、授权、幂等键原子提交。版本过期先重算，不把旧预览强行写进去。撤销用户动作与内部连带结果，但不能撤销之后发生的外部事实；按最新证据重算风险。

11. 可直接测试的状态与限制

  • 计划=当前正式已采用输入，预计=最新可确认的计算，实际=已发生证据；互不覆盖。
  • 计划编排可从中间开始；旅行正在执行时不允许反推改写已完成时间。
  • Query失败 / 无候选 / 确认停运必须不同结果。
  • 缺少路径时不能把两项目标时间之差全部算自由空档。
  • 不做AI推理必依赖：确定性规则和测试先行；未来推荐服务只能调用同一Preview/Adopt边界。

工程、安全、部署与 GitHub 硬性规范

1. GitHub是代码交付路径，不是部署服务器或数据库备份

每个阶段：确认新仓库 → fetch → 基于已审查main建feature分支 → 小步开发 → 真实测试 → commit → push → PR → 等待审查与用户合并确认。[S06]

必须报告：分支、HEAD SHA、远程对应SHA、PR URL、测试命令与结果、改动文件、已知限制、未完成项。只commit不push，不算完成交付；push失败不得说“已同步”。PR创建失败要明确，不用口头总结替代PR。

禁止：force push、直接改main、重置/清理未知工作区、覆盖他人变更、未经确认自动merge、提交密钥或本机数据、使用旧仓库作为新项目远程、擅自公开仓库。

建议核验命令（需先确认路径和remote）：

git status --short --branch
git remote -v
git fetch origin
git log -5 --oneline
# 已确认main有基线后再建分支；工作区有用户改动先停止可能覆盖的操作
# 阶段完成后核实本地与远程分支的提交一致
git rev-parse HEAD
git ls-remote origin refs/heads/<当前分支>

不要盲目执行git pull导致未审查merge；已确认分支可fast-forward更新。缺GitHub权限应走用户授权工具/正常认证，不要求用户把token贴聊天。

2. 空仓库PR起点

没有main首提交就没有通常PR的对比基线。用户先在新仓库创建最小README/.gitignore，或单独授权无业务代码的bootstrap。Codex不能在本包授权下直推main。

首轮只保留一个活跃开发阶段。上一阶段未合并时，不默认另开并行依赖分支；必须记录明确base SHA。

3. 账号与会话

首版只开普通用户与管理员；邀请邮箱白名单；无公众自助注册。

Magic Link工程要求：短期有效、一次性、随机高熵；存摘要而非可直接重放的原token；请求/兑换限流、统一响应防枚举；消费原子性。邮件预览GET不直接消耗凭证，最终兑换使用用户发起的安全请求；重定向目标做allowlist，不能任意open redirect。

浏览器首版优先HttpOnly/Secure/SameSite cookie会话，敏感写操作做CSRF/Origin检查；长期登录仍有服务端过期/撤销，不做永久JWT且不能撤销。[S08]

账号禁用必须阻止新登录并使已有会话失效。管理员强制注销所有设备时，下一次受保护请求立即重新认证；必要时停止对应用户的后台任务。初始管理员通过受控bootstrap命令建立，不写固定通用口令进seed。

管理员可以管理账号状态，但访问他人Trip/费用/文件仍拒绝。每个入口、worker用例、附件下载都检查归属；不能只依赖前端隐藏按钮。[S07]

未来原生客户端认证通过独立client adapter扩展，不能把浏览器cookie直接硬塞所有平台。P0/P1只记录方案边界，原生SDK后置。

4. 文件存储

ObjectStorage端口至少提供put/get/delete、私有访问授权或短期下载凭证、大小/类型元数据。数据库存key、owner、归属、文件名、MIME、bytes、createdAt，不存文件正文。

不做默认OCR、AI解析、内容索引、二维码识别。安全检查不等于业务提取：格式allowlist、大小/配额、扩展名与类型核验、路径清理、私有访问仍必须有。[S10]

原始文件不写web公开目录。默认不内联执行HTML/SVG/宏等主动内容。预览为受控查看，浏览器内容安全策略隔离；下载每次鉴权，短期URL设短过期。

限额是必须项，但具体值不是用户已确认产品规则：环境变量配置开发测试上限、注明暂定值，P5实测后确认。大于上限只影响该上传，不损坏Trip。

5. Web/API 与 Worker

必须两个进程，但同一机器/同一Compose可部署。不要求额外服务器、Redis或Kubernetes。

Job必须持久化在PostgreSQL：runAt/status/attempts/leaseUntil/uniqueKey/payloadRef。建议以行锁/租约领取，worker崩溃租约过期后可重试，使用SKIP LOCKED等机制时明示队列语义。[S09]

每个任务幂等、有限重试、退避、超时、失败可见、支持撤销。绝不把关键提醒唯一保存在setTimeout中。不得宣称“严格exactly once”：邮件等外部副作用需幂等键/投递回执，异常时避免盲目重发。

事务写业务和outbox；worker消费后生成NotificationEvent。用户手动停止监控时取消实时刷新/风险任务，但用户固定定时提醒不受影响。

首版通知事件持久化和站内可读即可；没有APNs/FCM/Web Push凭证时不得报告系统通知已可用。

6. Provider契约

  • 类型化返回OK / NO_MATCH / UNAVAILABLE / OUT_OF_COVERAGE / STALE / INCONSISTENT等，禁止全失败都返回[]。
  • 记录source、observedAt、validUntil、适用时区/位置、语义、是否估算；不得把候选/历史确认值伪装实时事实。
  • 配置超时、有限重试、缓存、并发限制和费用调用计数，具体TTL参考服务条款与场景；不固定“所有路线缓存一天”。
  • 备用源只在语义等价且可靠时接管；结果冲突不取均值，不拼不存在的路线。
  • 真实字段核验应在P4/正式UI前完成，不把所有Provider研究拖到最后。
  • 缺凭证可实现接口、fixture适配及失败测试；fixture必须显式标记，仅dev/test加载。

7. 网络边界

客户端无网或核心后端不可达：显示不可用/无法加载，隐藏旧行程；不做离线编辑队列。此前已产生但未同步改动可私下暂存，不能显示已保存。

网络恢复先与服务端同步当前版本，再加载关键状态。个别Provider未恢复时按局部未知展示，不能让“等待所有服务成功”造成永久无法进入。

客户端无网，不意味着服务器知道客户端的所有状态或停止一切任务。 worker按其开关、已有事实和新鲜度做可靠部分；位置相关结果无新鲜证据就暂停。此项投递/计费政策若需要细分，登记未决项，不扩大产品离线能力。

8. Dev / Staging / Production

三个环境逻辑隔离：数据库、账号、密钥、对象存储前缀或桶、邮件目标、任务表和端口不串用。Compose可用项目名前缀和独立env/volume。Production保留配置形状，不默认部署。

当前测试数据可丢失，但普通容器restart应保持数据；禁止默认启动时reset或drop。reset命令只允许明确测试环境+确认标志，拒绝production及不明连接。

P0服务绑定127.0.0.1；本地邮件捕获器仅dev使用。Staging邀请测试者前必须HTTPS、鉴权、真实可用邮件、受控外网入口。域名、网络穿透、邮件提供商未指定，不自动购买或暴露数据库端口。

Git只存.env.example、迁移、seed和基础设施定义；不存.env、数据库volume、附件、登录链接、用户位置。

9. 低成本与可观察性

首版≤5人，不把并发扩容方案提前实现成复杂系统。时间引擎有执行时间上限与指标；避免每秒对每个用户全图+全Provider刷新。

日志保留requestId、规则ID、错误码、job/版本与脱敏原因。无完整审计平台不等于不留错误或安全操作痕迹；不日志输出邮箱token、附件正文、详细长期位置。

Dev/Staging接受数据风险，本轮不自动异地备份或灾备演练。开始存真实数据前另设上线闸门：备份/恢复/监控/秘密管理/隐私与访问控制验收必须补齐。

10. 测试要求

单元测试、契约测试、真实PostgreSQL集成测试、API测试分层。时间fixture可控；外部网络不作为全部单元测试依赖。明确“已跑”“未跑”“失败”“环境阻塞”，不能修改预期、skip测试或削弱权限来获得绿灯。

每次涉及权限、Adopt原子性、日期归属、幂等、撤销、worker恢复，必须增加回归测试。生成本包不代表这些测试已运行。
