## O-01 / O-02 已确认（P2 前置规则）

以下规则替代 O-01/O-02 原先的未决状态；前置规则与 P2A/P2B 已合并 main。P2B 只实现了
当前相邻 Transport、失效历史与 resolved 时间存储。O-03/O-04/O-07 的产品规则现已确认，
P3A 已单独获权实施 sequence/DayOccurrence；DST 输入、自动生命周期、时间传播与 Provider 实现
仍须单独授权。

### O-01：首尾空白日期是临时编辑态

- Trip 不长期持久化首尾空白日期。
- 编辑器执行“添加下一天”或“添加前一天”时，可以临时显示一个空白编辑日期；它不算正式 Trip 日期范围、不建立 `DateOwnership`、也不占用自然日。
- 只有出现有效行程内容（例如 Visit、FreeAction、Transport 或其他真实行程实体）后，该日期才正式进入 Trip 日期范围。
- 用户没有添加有效内容就离开编辑时，临时日期自动消失，不要求额外点击删除。
- 原有首日或末日的最后一个有效行程内容被删除或移动后，日期范围向内收缩；连续多个首尾空白日全部收缩。
- V1 不提供“保留首尾空白日”的特殊开关。

### O-02：有效范围与自然日唯一归属

- Trip 的有效日期范围是最早一个有有效行程内容的自然日至最晚一个有有效行程内容的自然日；范围内部的每个自然日都属于该 Trip。
- 因此中间空白日仍由该 Trip 占用，不因没有内容而释放给另一 Trip；首尾临时空白日不属于正式范围。
- Trip 尚无任何有效行程内容时可以存在，但不占用任何自然日。新建 Trip 时输入的 `start date` 只是规划/编辑锚点，不得直接创建 `DateOwnership`。
- 必须区分编辑/规划日期锚点、实际有效 Trip 日期范围与 `DateOwnership`，不能把三者塞进一个含义模糊的 `startDate`。
- Trip note、todo、普通备注、Attachment、Expense、NotificationEvent 或用户偏好单独存在时不撑开范围；若未来 Task/Expense 附着于有效行程实体，仍由该实体决定日期范围。跨午夜/跨时区 Day 投影留给 O-03。
- 同一账号一个自然日最多属于一个 Trip。范围扩展发生冲突时不得重复占用、静默覆盖或自动合并，必须返回明确冲突；合并、调整或取消由未来用户流程决定。

## O-03 已确认：timeline、日期卡、当地时区与 DST

O-03 在产品规则层面已解决。本节冻结产品语义。PR #8 本身不授权实现；其后 P3A 已单独获权落地
DayOccurrence/sequence migration，但不代表跨日投影或 DST 输入解析已经实现。

### 真实顺序与跨时区显示

- 整趟旅行的真实先后顺序由独立 timeline sequence 表达，不能以 `localDate + localTime`
  作为最终排序真相；已有明确 instant 时，真实时间先后按 instant 判断，sequence 不得与其矛盾。
- `localDate` / `localTime` 只负责当地显示。跨时区后当地钟点变小，不代表行程倒序，也不得为了
  让钟点递增而篡改时间。
- 只有真正发生时区变化的 Transport 卡片需要显式显示出发/到达时区和“时区切换”；进入新时区
  后的普通卡片不重复标注同一时区。
- 若跨时区后 localDate 不变但当地时间回拨，仅此变化不创建第二张同日期卡；时间轴可在同一卡中
  显示从较大钟点到较小钟点，并由跨时区 Transport 解释回拨。

### 跨日 Transport 与日期卡

- 一条连续跨日或跨多个自然日的 Transport 始终是同一业务实体：同一 ID、同一份
  PLANNED/ESTIMATED/ACTUAL、费用、状态和备注；它可以投影到多个日期卡，但不能复制数据库记录。
- 被连续 Transport 完整覆盖的中间自然日必须有日期卡，可概念性称为“交通占用日”；该日期属于
  Trip 正式范围并建立 `DateOwnership`，且不能再加入 Place、FreeAction 或其他普通行程内容。
- Transport 只投影到它按真实 timeline/sequence 经过的日期卡，不能只按相同 `localDate` 匹配。

### 日期回拨、重复日期卡与归属

- 跨国际日期线导致到达 localDate 早于出发 localDate 时，保留真实当地日期，并按真实 sequence
  生成带“日期回拨/跨日期线”提示的新日期卡；不得把日期强行改大。
- 同一个 `localDate` 可以在 timeline 中出现任意多张独立日期卡，不设“两张”的上限。P3A 正式
  使用持久 `DayOccurrence` 与 Trip-scoped sequence。
- 新增或编辑内容必须指向具体日期卡身份，不能仅凭 `localDate` 把内容放进较早出现的同日期卡。
- 多张同日期卡不产生多份日期归属；`DateOwnership` 仍只表达“该用户的这个自然日属于哪个
  Trip”。日期卡可以重复，不代表跨 Trip 或同 Trip 可以重复占用自然日。

### 旅行执行中的当前当地时间

- 当前当地时区依次取：可靠设备定位、设备当前时区、当前行程地点的已知时区上下文；永远不使用
  服务器默认时区猜测。
- 定位或时区证据只能帮助确定当地日期、当前当地时间、提醒和时间轴上下文；“处于某时区”不等于
  已到达具体地点，不能据此伪造 Visit 完成、实际到达或其他 ACTUAL 事实。

### DST 重复时间与不存在时间

- Provider、航班、铁路等可靠结构化数据若已经给出明确 instant 或 UTC offset，系统自行确定实际
  时刻，不再询问用户选择前一个/后一个当地时间。
- 用户只手工输入一个在 DST 回拨日重复出现的当地钟点时，系统不得猜测，必须让用户选择前一个
  或后一个 occurrence。UI 可以辅助显示各自 UTC offset，但不要求用户理解 DST 术语，也不允许
  默认选择其中一个。
- 用户输入因 DST 跳时而不存在的当地钟点时，明确提示该时间不存在；不得自动改为后一小时、
  向前或向后平移，也不得静默接受。
- 外部可靠数据已有明确 instant 时直接使用；只有当地钟点且信息仍不足以唯一确定 instant 时，
  保持歧义并返回明确错误，不猜测。

### 实施状态

- P3A 已获授权实现 `DayOccurrence` 数据结构与从 `localDate + position` 到独立 sequence 的无损
  migration；实际交付证据见 `docs/status/P3A.md`。
- 跨日 Transport 与日期卡关系的最终存储/投影。
- DST 重复/不存在时间的输入解析 command 与 UI。

这些是实现设计和施工项，不再是产品规则未决项。

## O-04 已确认：受保护安排的来源

- 系统不解析备注、附件、待办或自然语言去猜用户是否购票/预约。“已经订了”“想订”“可能18点”
  等文字单独存在时都不是受保护安排。
- 第一类受保护来源是系统已有的可靠结构化事实，例如已采用的固定列车/航班、结构化确认的预约
  或门票时间，以及其他明确固定服务。
- 第二类来源是用户主动、明确的轻量标记，例如“已预订”或“时间固定”。V1 不要求订单号、商家
  截图、付款凭证、OCR 或完整订单模块。
- 普通计划仍可作为相对可调整安排；被保护安排发生冲突时，系统优先尝试保住该时间，但“保护”
  不等于绝对禁止修改。现实条件不允许时必须展示冲突并交由用户决定，不能伪造问题已解决。
- Provider/Booking integration 将来如何取得可靠结构化确认属于实现问题，不再阻塞核心产品逻辑。

## O-05 已确认：体验约束与推荐排序

- 系统不设“餐饮至少 60 分钟”等跨场景全局体验最低值。`90 → 20` 分钟可以作为显著损失展示，
  但没有用户约束或可靠事实时不能据此把候选判为非法。
- 用户对具体活动明确设置最低体验时长后，该值才成为硬约束；低于该值的候选不可行。
- 推荐先排除违反事实、受保护安排和用户硬约束的方案，再优先保住固定/受保护内容，以最小改动为
  基线，比较成本、剩余体验、时间收益、风险和影响范围。不存在“永远最便宜”或“永远最快”的
  全局优先级，也不固定一套跨场景评分权重。
- 每个推荐必须解释关键取舍与事实依据。默认给 1 个主推荐和最多 2 个可靠备选；只有 1 个可靠
  候选就只给 1 个，没有可靠候选就明确说明没有可确认方案，不为凑数造方案。
- 已知偏好可以影响可行候选之间的排序和说明，但不能替代事实、受保护安排或用户硬约束。
- 上述规则已解决产品判断；RecommendationPolicy、评分/比较实现与 UI 尚未授权、未实现。

## O-06 已确认：外部预约调整的用户确认边界

- 系统可以发现冲突、建议用户把外部预约调整到新时刻，并提醒用户自行联系商家或外部服务。
- 用户完成外部操作后点击“已调整”，即可作为本产品继续生成新计划的用户确认；V1 不要求外部
  API 回执、订单号、截图、付款证明或 OCR，也不为此建立复杂的外部状态机。
- 该确认只能表述为“用户确认已调整”，不能写成“商家官方确认”“有位”或其他未经真实外部数据
  支持的事实。若用户之后发现调整失败，可再次修改或选择其他方案。
- 未来真实 Provider 可以增强核验和自动化，但不是 P3/P4 核心流程的产品逻辑前置条件；相关外部
  集成仍未实现。

## O-07 已确认：旅行自然结束，不要求用户证明

- 用户创建旅行计划后，系统按计划提供服务。计划日期结束后，Trip 可自然进入“已结束”，即使
  后几天没有打开 App、没有定位、没有 Actual 或没有补记录。
- 不向用户追问“到底去了没有”，不创建“待确认是否旅行”“等待结果”或“记录不完整需要处理”
  的用户任务，也不要求补作业。
- Actual、定位和 App 使用记录用于旅行中提醒、当前状态、风险、后续调整和历史回看；有多少保存
  多少，缺少部分保持 unknown，但它们不是证明旅行发生或进入“已结束”的门槛。
- 只有用户主动明确表示“这趟旅行没去”，才标记 `NOT_TAKEN`。无定位、未打开 App、无 Actual
  或没有执行数据都不得自动推断未执行。
- 用户可见生命周期保持“计划中 / 进行中 / 已结束 / 未执行（仅用户明确）”。底层如需技术状态，
  不得转化为用户必须处理的确认任务。自动生命周期代码仍未实现。

## O-08 已确认：提醒与实时监控

- 同一个稳定风险事件默认只主动提醒一次。只有严重等级升级、新重要事实出现，或用户主动 snooze
  到期且风险仍在时，才允许再次主动提醒。
- “知道了，继续按这个计划”只接受当前风险等级；同等级保持安静，但不永久关闭该类风险。风险
  升级是状态变化，不以每分钟 ETA 变化或全局“减少 X 分钟”阈值判断。
- 实时计算可提前静默运行，只在真正需要行动的窗口打扰。固定提醒与实时监控独立；关闭实时监控
  会停止位置、动态 ETA、动态最晚出发、风险推断和延误联动，但不会删除固定提醒。
- 定位权限丢失使监控进入 LIMITED，`userEnabled` 仍为 true；固定提醒继续，权限恢复后可恢复实时
  能力。挂起、离线或后台中断后先重同步，旧位置不冒充当前事实，中间过程保持 unknown。
- 当前进度 unknown 不阻止固定提醒。过期固定提醒不补发旧指令；固定与动态提醒目的相同时去重。
  多提醒并发时优先明确时窗和严重后果，正文采用关键行动加“还有 N 个待办”的摘要。
- 本机通知、Worker 与未来 Push 都只是投递 capability，不承诺任何平台 100% 到达。

## O-10 已确认：网络、Provider 与核心服务故障

- 外部 Provider 独立降级；铁路/航班/地图故障只影响对应实时或路线能力，其他 Trip 内容继续可用，
  受影响事实标 unavailable/unknown，不伪造准点、可达或有路线。
- 失败时提供独立人工查询出口，例如航空公司、机场、运营商官网、Google Maps 或 Apple Maps。
  外部跳转只帮助用户查询，网页内容不会自动成为系统事实。
- 核心 TRAVEL 后端不可用时显示服务暂时不可用，不把旧缓存伪装成当前可靠行程；V1 不做完整
  离线模式。
- 托底方式是带生成时间的静态行程图片，可保存到相册或分享，且明确后续修改不会同步。旅行前
  一天或第一次进入“即将开始”时提醒一次保存，不每天重复。

## O-11 已确认：历史回顾、分享与复制

- 回顾默认相信用户最终保留的历史行程，不要求定位、Actual、App 打开记录或额外证明。只有明确
  跳过、取消、删除/修正为未发生，或可靠事实确认未执行时才排除。
- 回顾主线是地点、FreeAction/特别体验及实际/最终顺序。普通交通不展示；交通本身是旅行体验时
  可作为体验内容进入，但不是底层 TransportEdge 日志。
- 用户可编辑历史行程并重新生成回顾。回顾不是第二套事实数据库；旧图片和分享快照不会随历史
  编辑自动变化。
- 轻量分享默认不含交通细节、待办、风险、订单、费用、私人备注或附件。分享链接是独立静态快照，
  默认长期有效、匿名可看，由用户主动停止；新旧版本互不自动关闭。
- 复制时才要求登录。复制生成新的计划中 Trip，用户选择日期、人数和名称；地点/顺序、整体日期
  平移及当地时间作为参考，原 Actual 不成为新用户事实，私人数据与历史执行事实不复制。
- 跨时区/日期线回顾按真实 sequence / DayOccurrence 展示，允许当地日期回拨，不重排，也不强制
  插入航班交通卡。

修改O-01/O-02必须一起检查：Trip日期、Day构建、空白日、复制、分享、合并、生命周期、用户内唯一归属与原子事务。

修改 O-03 必须一起检查：timeline sequence、DayOccurrence 身份、本地日期、UTC、持续时长、
跨日 Transport 投影、DateOwnership、复制平移、日期冲突、提醒时刻与按日费用。

修改 O-04 必须一起检查：待办极简、附件不解析、订单模块后置、用户明确标记、可靠结构化事实与
受保护安排风险。

修改 O-05 必须一起检查：硬约束可行性、受保护安排、最小改动、成本/体验/时间/风险/影响范围、
解释、偏好与候选数量；不得重新引入全局最低时长或固定评分权重。

修改 O-06 必须一起检查：预约建议、用户外部操作、用户确认来源、事实标签、失败后重新调整与
Provider 能力；不得把用户确认伪装成商家官方确认。

修改 O-07 必须一起检查：Trip 生命周期、监控停止、Actual/unknown、历史回看、NOT_TAKEN 与
用户可见状态；不得重新引入证明旅行或补记录任务。

修改 O-08 必须一起检查：稳定事件键、严重等级、新事实、用户接受/snooze、固定与动态提醒、
LIMITED、断点恢复、过期提醒、去重、优先级和投递能力声明。

修改 O-10 必须一起检查：Provider 独立降级、实时事实 unknown、外部人工查询出口、网页事实边界、
核心后端故障态、缓存与静态图片备份。

修改 O-11 必须一起检查：O-03 sequence/DayOccurrence、O-07 unknown、历史编辑、回顾投影、
Transport 体验语义、静态快照、匿名访问、停止分享和复制隐私边界。

## 闸门与范围

- **G0/P0开始：** 用户已经授权导出与首轮开发要求。Codex核对空白目录和目标仓库；无地址不得发布到旧库。
- **G1/P0验收后：** 用户确认再做P1，核对真实依赖/部署可用性。P0文档不是全部未来阶段的自动执行授权。
- **G2/P2前：** O-01/O-02 与 P2A/P2B 已合并 main。O-03/O-07 产品规则现已确认，但相关高级
  timeline 与生命周期实现不在 P2 范围。
- **G3/P3前：** O-03 至 O-07 的核心产品判断均已确认，当前没有已知的 P3 产品逻辑阻塞。
  DayOccurrence/sequence migration、跨日投影、DST command/UI 和生命周期是尚未实施的工程工作；
  RecommendationPolicy 和预约确认流程同样尚未实现。信息不足时仍返回
  `UNSUPPORTED_SCENARIO` / `AMBIGUOUS_TIME_INPUT`，不得猜测。P3 代码需单独授权。
- **G4/P4前：** O-04/O-05/O-06 产品规则已确认；仍需完成 Provider 字段探针、版本和幂等设计。
  用户确认只能标为用户确认，真实外部凭证缺失时不得伪装成商家官方确认。
- **G5/≤5人测试前：** O-08/O-10/O-11 产品规则已确认；仍须让鉴权、会话撤销、数据隔离、
  HTTPS/邮件、持久任务、故障提示、提醒去重、图片备份、分享权限和测试数据标志通过真实实现验证。
  O-09 保持 Deferred，须在对应上线能力前逐项确定。
- **进入真实旅行使用前另开上线检查：** 备份恢复、可靠性与原生通知/位置能力未做完，不能仅凭后端测试就宣称可保障旅途。
