# P5E2 Batch 1 — Ground Transit Execution Foundation

Status: P5E2 Batch 1 merged through PR #30; main baseline `e4685c5f729e27b2f1a8cab65c8c76393a01178d` (verify, Compose verification, and P5B acceptance successful). Starting main: `78cea5c481eea594943a30f0285b2e47698558be`.

This batch binds adopted RAIL/BUS legs to an immutable, provider-neutral execution baseline at Route Adopt. The baseline retains the selected service class, exact fixed-service identity when available, or high-frequency line/direction/boarding/alighting identity and the adopted execution window. Existing routes are not guessed into a new identity: missing P5E2 metadata is shown as `UNKNOWN`. The leg record has no TransportEdge FK, so replacement and Undo do not erase its historical observations or state transitions. Trip deletion still cascades private data.

`FIXED_SERVICE` accepts only an exact canonical `serviceIdentityKey`. `HIGH_FREQUENCY` matches the adopted line, direction, hubs, and execution window, never a particular vehicle. Neither a Provider departure nor a location movement claims that the user boarded a particular service. Fixed-service Provider facts can add ESTIMATED and ACTUAL TemporalValue with a stored observation ID as sourceRef; an existing ACTUAL is never overwritten. High-frequency headway and next departure stay in execution context, not a fabricated selected-service ACTUAL.

The versioned `ground-transit-execution-v1` policy uses a five-minute realtime freshness limit. For a 3–5 minute headway, the boarding wait reserve is five minutes; a fresh reliable next departure in two minutes replaces it with two minutes. ETA range is reported separately. Adopted `minimumTransferSeconds` means the complete transfer **after alighting this leg and before the next leg**, not access before boarding this leg. It is never added at both boundaries. `boardingAccessMinimumSeconds` is independent adopted access evidence; zero is allowed only when the normalized provider explicitly establishes it. Unknown critical access or transfer yields null minimum, `UNKNOWN` feasibility, and an existing `UNKNOWN_EXECUTION_MARGIN` risk only for a protected downstream fixed service. No five-minute transfer fallback is used for feasibility. Safety reports basis and reason codes without a confidence percentage. Normalized observations are appended, ordered by fetchedAt/identity/facts hash, and never contain raw GPS. Service failure remains `GROUND_TRANSIT_PROVIDER_UNAVAILABLE`, not “no route”: fresh cached observations can still be used, and stale/missing observations cause baseline risk reevaluation on the existing monitor cadence without inventing a Provider fact.

Leg states are `PENDING`, `IN_PROGRESS`, `ARRIVED_PENDING_HANDOFF`, `COMPLETED`, `NO_LONGER_FEASIBLE`, and `UNKNOWN`. Location can update a derived leg state only under the current LOCATION_ASSISTANCE revision; AUTO_RECORD remains independent. Destination arrival alone is not completion; context handoff is required. A fixed service that has already departed before the user's known arrival, or is cancelled, can become no longer feasible; missing one high-frequency vehicle does not. Historical transitions are retained.

The existing ExecutionRisk reconciliation handles system-minimum headway/transfer and fixed-service consequences; P5E2 does not create a second risk table or notification policy. Ground realtime deterioration needs sustained, consequential evidence before proactive estimated-time risk. Active Trip-scoped `GROUND_TRANSIT_MONITORING` is explicit opt-in, independently revisioned and fenced. Worker jobs bind the AdoptedRoute and capability generation. Pause/Stop and natural Trip completion cancel obsolete jobs; manual refresh remains available without monitoring. The synthetic Provider and two-leg route are Dev/Test-only with `SYNTHETIC_CI_ONLY=true` and never call a paid Provider.

API: `GET /trips/:tripId/execution/ground-transit` and `POST /trips/:tripId/execution/ground-transit/:transportEdgeId/refresh`. Each leg exposes separate `safety.boarding` and `safety.transferToNext` assessments; the latter is null without an onward connection. Their minimums, feasibility, reason codes, and reevaluation flags are never merged into one total. Existing `/trips/:tripId/assistance/GROUND_TRANSIT_MONITORING` handles opt-in and lifecycle. Migration: `20260929100000_p5e2_ground_transit_execution_foundation`. Clean and populated migration tests explicitly preserve legacy ACTUAL, Trip version, and opt-in state without backfill.

Still open: F-05/F-06/F-07/F-08. Batch 1 does not classify operational cancellation, early departure, material delay, platform changes, skipped adopted stops, or later service recovery; these are the separate Batch 2 scope. Not included: real Ground Transit Provider entitlement/integration, exact ridership inference, automatic route change/Adopt, Push, native background location, official UI, Staging, or Production.
