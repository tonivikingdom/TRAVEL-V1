## 0. 产品宪法 / North Star

终极目标：基于用户自己的需求、偏好与约束，为用户规划一套对这个用户而言尽可能合适的旅程，并尽可能帮助用户把这套行程顺利落地；减少行前与旅行中的繁琐操作；旅行结束后留下真实、尽可能完整的旅行记录。

一句话愿景：
> 根据用户真正想要的旅行，帮他规划好、执行好、少操心，并留下真实而完整的旅行记录。

核心原则：
- 计划服务于旅行，旅行不服务于计划；
- 系统是助手，不是监督者；
- 机械、可验证的工作尽量自动化，偏好与取舍由用户决定；
- 用户偏离计划本身不是错误；
- 重大变化优先最小改动；
- 真实性优先于形式完整；
- 不完整 ≠ 错误；
- 没有可靠依据的信息不能编，估算必须标明；
- 用户选择高风险方案可以继续，系统负责说明后果；
- 产品逻辑先想完整，版本功能分阶段开放。

## 1. Trip 创建与基础属性

### 1.1 新建旅行最小字段
新建旅行只要求：
- 旅行名称；
- 开始日期；
- 人数。

规则：
- 开始日期必填；
- 人数必填，默认可由界面给出合理值，用户最终确认；
- 结束日期不要求填写，初始结束日期 = 开始日期；
- 随 Day、跨日节点和实际行程自动扩展/收缩；
- 目的地/国家/城市不是必填字段，由行程地点自动推导；
- 旅行名称任何生命周期均可修改；
- Trip 人数可修改，前期主要影响费用，不自动改地点/时间/交通。

### 1.2 Trip 级信息
保留：
- 旅行总备注：可选纯文本，任何阶段可编辑；
- 旅行总待办：标题、完成状态、备注、可选提醒时间；
- 无提醒时间的总待办只在旅行总览展示，不主动通知；
- 用户设定具体提醒时间后才通知。

### 1.3 用户级基准货币
- 基准货币属于用户级全局偏好，不属于 Trip；
- 与 UI 语言、目的地、系统地区解耦；英文界面也可以 CNY 为基准货币；
- 用户修改基准货币后，所有旅行汇总视角同步切换；
- 原始金额与原始币种永远不变。

## 2. Day、日期范围与 Trip 日期归属

### 2.1 Day 扩展
- 新建后先有开始日期当天；
- 通过「添加下一天」向后扩展；
- 可以「添加前一天」向前扩展，不移动已有行程；
- 可以在中间「插入一天」，插入点之后行程整体顺延，日期相关信息重新校验；
- 可以「将后续行程整体提前一天」，当地钟点保持，日期相关信息重新校验；
- Day 不作为普通可删除对象：头尾空白日自动收缩，中间空白日合法保留；新建空白Day的编辑保护与收缩时机尚待确认，不得创建后立即删除（O-01）。
- 日期整体移动不能从跨日地点、自由行动或跨日交通中间切断连续关系。

### 2.2 修改出发日期
- 旅行尚未开始执行时允许整趟改期；
- 整体平移的是当地日历日期，不做 UTC 机械平移；
- 各节点原当地计划钟点保留；
- 具体班次、营业时间、季节运营等按新日期重新校验；
- 进行中不能整趟改出发日期，只调整尚未发生部分；
- 正常已结束旅行不能靠改日期重新激活，需要复制为新旅行。

### 2.3 日期唯一归属
核心规则：
> 同一个自然日，同一账户只能归属于一个 Trip。

补充：
- 两趟旅行日期连续不代表自动属于同一 Trip；用户建立两个 Trip，默认就是两个；
- 当某 Trip 扩展到已经归属于另一个 Trip 的日期时，不能先创建第二份同日期 Day；
- 先提示日期冲突，用户可选择合并旅行，或先处理/释放原 Trip 的该日期；
- “旅行日期区间重叠即禁止”的旧规则废弃，改为“自然日唯一归属 + 冲突解决”。

### 2.4 合并旅行
- 日期冲突时可触发合并；无冲突时也允许用户主动合并；
- 合并不要求日期连续，中间可形成合法空白日；
- 合并是无损改变 Trip 归属，不是复制；
- 两边已有地点、自由行动、交通、计划/预计/实际时间、执行事实、备注、待办、费用、附件等全部保留；
- 已发生部分保持历史事实锁定；未来部分保持计划状态；
- 如果前面已有实际发生内容、后面还有未来内容，即使中间为空白日，合并后的 Trip 整体仍可处于进行中；空白日不自动切断 Trip；
- 合并时用户重新输入新的旅行名称；
- 两边默认人数不同则由用户重新确认合并后 Trip 默认人数；
- 两边总备注、总待办无损合并；
- 合并后无法再拆分为原来的两趟，执行前必须明确提醒不可逆；
- 不提供“拆分旅行”能力。

## 3. 地点、自由行动与相邻交通

### 3.1 地点
- 空白日可添加第一个地点；搜索选中后立即加入，不强制先配完整时间；
- 地点可插入或末尾追加；
- 同一真实地点可重复出现，每次是独立 Visit；
- 地点卡支持同日拖拽排序；只移动地点，不把原交通固定绑走；
- 拖动完成后只重算发生邻接变化的边；
- 删除地点不二次确认，提供短暂单步 Undo；
- Replace 地点在原位置替换，旧相邻交通失效，新边待选择；旧备注不继承；
- 地点名称/地址（身份）不直接编辑，要改变身份用 Replace。

### 3.2 自定义地点
- 最小创建信息 = 名称 + 可定位的位置；
- 有可靠地址则显示，没有正式地址但坐标可靠也允许创建；
- 不为了完整性虚构地址；
- 电话、分类、营业时间等不是必填。

### 3.3 自由行动
“自由行动”是特殊行程节点，不是假 Place：
- 固定名称“自由行动”；
- 无 Place ID/固定地点身份；
- 支持计划/实际时间、备注、待办、费用、🔒、拖拽、删除、撤销；
- 可首尾、可跨日；
- 不因为定位或消费自动拆成地点；
- 用户可事后转换为正式地点或拆为多个正式地点+交通；
- 若两个自由行动因删除中间地点而相邻，不自动合并，轻提示用户决定；
- meaningful gap（当前测试阈值约 30 分钟）可询问是否填入自由行动，但不自动填满。

## 4. 交通、采用与换乘节点

### 4.1 邻接交通
- 当前有效时间轴只维护相邻行程节点之间的有效交通；
- 插入/删除/拖拽只影响邻接变化的交通；
- 旧失效交通进入历史，不参与当前排程；
- 路线查询/预览绝不修改正式行程；点击 Adopt 后才落地。

### 4.2 多段交通展开
若 A→D 方案实际为 A→公交→B→火车→C→公交→D，采用后主时间轴展开为 A→B→C→D。
- 真正上下车/换乘/等待的节点可成为正式交通生成节点；
- 单纯途经站不展开；
- 步行是交通段；
- 同站内部换乘只保留一个站点卡，内部停留包含下车、站内步行、找站台、等待；
- 用户计划地点与交通生成地点底层来源必须区分；
- 重规划可替换交通生成节点，但不能静默跳过用户计划地点。

### 4.3 固定班次是事实型时间锚点
- 已采用的具体火车、航班、巴士等班次，其出发/到达时刻天然成为事实型锚点；
- 用户不需要再手动🔒一次；
- 要改变该时间，需要换班次/换交通，不能直接把班次时间改成任意数字。

## 5. 时间模型与多方向排程

### 5.1 三层时间
Planned / Estimated / Actual 三层互不覆盖：
- Planned：正式计划；
- Estimated：当前动态预计；
- Actual：真实事实。

### 5.2 地点三变量
普通地点核心关系：
> 到达时间 + 停留时长 = 离开时间

任意两个可推第三个：
- 到达 + 离开 → 停留；
- 到达 + 停留 → 离开；
- 离开 + 停留 → 到达。

但必须同时记录每个值的来源/语义，至少能区分：
- 用户正式计划值；
- 用户约束/目标；
- 已采用交通推导结果；
- 系统建议；
- Estimated；
- Actual。

### 5.3 目标 vs 当前方案结果
例如：
- 用户要求“23:30 前到浦东机场”；
- 当前选定路线实际预计“23:00 到”。

二者必须同时保留：
- 23:30 是用户条件；
- 23:00 是当前方案结果；
- 后续方案变成 23:10 仍可能满足原目标；
- 不能用方案结果覆盖用户条件。

同理：
- 用户希望南京南至少预留 20 分钟；
- 当前交通算出实际停留 25 分钟；
- 20 分钟继续作为要求，25 分钟是方案结果。

### 5.4 从任意方向推导
同一套引擎必须支持：
- 从头向后推；
- 从尾向前反推；
- 从中间锚点同时向前/向后推；
- 在同一规划过程中随时换方向，不需要切换“模式”。

真实交通不是纯算术：
- 先计算查询条件（如最晚到站、最早出发）；
- 再查询真实路线/班次；
- 用户采用后，真实交通结果回填相邻地点时间；
- 到得比目标更早，显示真实时间，不为了凑目标伪造时间。

### 5.5 修改时间后的自动化
例：南京南当前 19:56 到，G93 20:21 出发，停留25分钟；用户把到达时间改成19:30。
- 20:21 班次事实保持；
- 停留自动重算为51分钟；
- 原前段交通若仍19:56到，则与新计划19:30冲突；
- 系统自动以“到达南京南 ≤ 19:30”为条件重新查询前段交通；
- 无班次交通仅可在既有选择不变且无歧义时刷新估算；新路线、方式变化或新的费用选择仍需采用，不自动订车。
- 有具体路线/班次选择的交通，系统自动查询、推荐，但用户确认 Adopt 后才替换。

## 6. 🔒、客观约束、缓冲与风险

### 6.1 约束优先层
当前原则：
> 客观规则/事实 > 用户明确保护的约束 🔒 > 用户正式计划值 > 尚未采用的系统建议

说明：用户仍可选择冒险，但系统不能把客观事实降级为不存在。

### 6.2 🔒 的用途
🔒用于用户自己的重要意图：
- 固定时间；
- 最早/最晚；
- 最低停留；
- 个人预留；
- 重要偏好。

固定班次本身不需要再🔒。

### 6.2.1 受保护安排的确认来源

- 系统不解析备注、附件、待办或模糊文字去猜预约/购票事实；备注写“已订”本身不建立保护。
- 受保护安排只来自可靠结构化事实（例如已采用固定班次、结构化确认的预约/门票时间），或用户
  主动明确标记“已预订 / 时间固定”。
- 首版保持轻量，不要求订单号、截图、付款凭证、OCR 或完整订单模块。
- 冲突时优先尝试保住受保护时间，但保护不等于绝对禁止修改；无法满足时展示冲突并让用户决定，
  不得伪造“已解决”。

### 6.3 缓冲
不做全球统一“火车20分钟、航班2小时”的死表。按具体场景维护：
- mandatory：客观必须值；
- recommended：更稳妥建议值；
- 用户自己的预留要求。

如果只有 mandatory：正常/红；只有 recommended：正常/黄；缺依据不制造红线。

不同安排约束语义不同：
- 火车/航班/末班车等不等人，客观截止更硬；
- 餐厅预约可能有迟到容忍，但没有可靠规则时不能瞎猜；
- 没有明确硬规则时，把“时间非常紧张”交给用户判断，用户可保持不改；
- 用户已接受同一层级风险后不重复催，除非风险升级/事实变化。

## 7. 冲突求解与方案推荐（持续迭代模块）

### 7.1 核心目标
系统不能只报“还差20分钟”，而应该主动把可行妥协算出来。
> 系统负责算时间账和后果，用户负责选择自己愿意接受的妥协。

### 7.2 最小改动优先
当中间停留延长导致后续冲突：
1. 先检查能否只改局部交通解决；
2. 若可行，给出时间收益、额外费用、风险；
3. 用户接受 → 只改这一段；
4. 用户拒绝/代价不可接受 → 再向前或向后传播调整；
5. 后续预约/活动本身可调整时，也可成为候选解，但要计算对更后面时间轴和体验的影响。

例：美术馆17:10离开、餐厅17:30预约；巴士40分钟，打车20分钟但贵很多：
- 优先可以提示“换打车即可保住当前美术馆停留和17:30预约，预计增加费用800”；
- 用户接受则局部解决；
- 不接受再考虑提前前段到达、压缩地点、修改预约等。

### 7.3 方案不能只看可行性，还要看质量
例如把餐厅改到18:00：
- 若还能吃约60分钟，可能是合理妥协；若只能吃20分钟，系统应清楚展示 `90 → 20` 的体验损失；
- 60分钟或20分钟只是用于比较的例子，不是全局最低体验时长。没有用户要求或可靠事实时，系统
  不能武断地把20分钟方案判为非法；
- 用户对该活动明确设置最低时长后，该最低时长才成为硬约束；
- 方案推荐必须评估“剩余体验”，而不是只求时间可行。

### 7.4 推荐排序
推荐先排除违反事实、受保护安排或用户硬约束的不可行候选。对于剩余可行候选：
1. 优先保住固定、受保护安排和用户约束；
2. 以最小改动为基线；
3. 再共同比较费用、剩余体验、时间收益、风险和影响范围；
4. 给出关键取舍与事实依据的解释。

已知用户偏好时，允许基于偏好标出“更适合你的方案”，但偏好不能覆盖事实或硬约束，也不能
自动采用方案。不能把“最便宜”或“最快”天然当成最优，不固定一套跨场景全局评分权重。

### 7.5 方案展示数量与打扰尺度
- 默认 1 个主推荐 + 最多2个可靠备选；只有1个可靠候选就只展示1个，没有可靠候选就明确说明
  没有可确认方案，不为凑数编造；
- 都不接受，用户可自行调整；
- 用户拒绝/关闭推荐面板后，同一风险进入安静辅助：只实时更新剩余缺口和风险，不再主动弹新方案；
- 用户主动“帮我优化”才重新生成方案；
- 同一冲突解决后，风险标识静默消失，不弹“优化成功”；
- 风险明显升级/事实变化 = 新风险事件，可重新提醒，并必须基于新现实生成新方案。

### 7.6 Preview / Adopt
所有涉及：
- 换具体交通；
- 增加显著费用；
- 改预约；
- 改重要行程；
都必须 Preview → 用户确认 → Adopt。

计算可以自动、查询可以自动、推荐可以自动，但决策不能被系统静默采用。

### 7.7 外部预约调整

- 系统可以发现冲突、建议新的预约时刻，并提醒用户自行联系餐厅、场馆或其他外部服务；
- 用户完成外部操作后点击“已调整”，即可作为本产品继续生成新计划的用户确认；
- V1 不要求外部 API 回执、订单号、截图、付款证明或 OCR，也不建立复杂外部预约状态机；
- 用户确认只能标记为“用户确认已调整”，不能称为商家官方确认、有位或已由 Provider 核验；
- 若用户之后发现外部调整失败，可以再次修改或选择其他方案；未来 Provider 核验属于增强能力。

## 8. 执行生命周期与实时监控

### 8.1 Trip 生命周期
- 到达旅行开始日期后，系统默认 Trip 已进入进行中；
- “进行中”不等于从00:00开始持续定位；
- 用户晚出发、睡过头、第一天被打乱，仍属于进行中的意外情况；
- 系统不能仅因未检测到执行证据就自动判“未执行”；
- 计划周期结束后自然进入“已结束”，不要求用户证明旅行发生；
- 没开 App、没有定位、没有 Actual 或未补记录都不产生“是否去过”追问；
- Actual 与执行证据有多少保存多少，缺失保持 unknown，不作为结束门槛；
- 只有用户主动明确表示“这趟旅行没去”，才标记“未执行”。

### 8.2 自然结束与历史记录
- 计划日期结束后 Trip 进入历史“已结束”；已有 Actual 继续作为事实保留，未知部分仍为 unknown；
- 不把“记录不完整”作为用户必须处理的主要状态，不要求补作业；
- 不因缺少证据进入“待确认是否旅行”或自动归为未执行；
- 正常已结束旅行不可通过改日期重新激活。

### 8.3 实时监控启动
状态和监控分离：
- Trip 可以已经进行中，但实时监控尚未启动；
- 用户当天主动打开旅行 → 可启动后台计算；
- 当天第一个有明确计划时间且值得监控的节点进入临近窗口 → 可启动后台计算；
- 无明确时间 + 用户未打开 App → 不主动全天监控。
- 实时监控可以提前静默计算，但只有进入真正需要用户行动的窗口才主动打扰。

### 8.4 监控持续与停止
- 一旦启动，可在锁屏/退出 App 后后台继续；
- 只有仍有实时执行价值时持续；
- 无剩余实时判断价值时自动停止，即使最后事实未确认也可留下未知；
- 跨日交通/地点/自由行动有执行价值时可跨0点继续；
- 用户可主动“停止实时监控”，只关闭实时执行层，不结束旅行；
- 用户主动停止后跨天保持关闭，直到用户主动重新开启；
- 系统自然停止后，后续满足条件可自动恢复；
- 固定提醒与实时监控是独立能力。用户主动停止实时监控后，位置、实时交通刷新、动态 ETA、动态
  最晚出发、自动到达判断、实时风险推断和延误联动都暂停；预先设置的固定提醒仍保留，除非用户
  单独关闭。

### 8.5 定位/后台能力失效
- 定位权限失效 ≠ 用户主动停止监控；
- 定位权限失效时 `userEnabled` 仍为 true，实时层进入 `LIMITED`；固定提醒继续，仅暂停依赖实时位置
  的能力，权限恢复后可自动恢复实时能力；
- App 被挂起、设备离线或后台执行中断后，重新打开/联网时重新同步当前时间、位置和交通状态；
- 旧位置不能冒充当前实时位置；中断期间未知事实保持 unknown，不续算旧 ETA、不补造轨迹，也不猜
  用户是否停留或已经到达。必要时提示一次“实时监控曾中断，已重新同步”。

### 8.6 风险事件与提醒（O-08 产品规则已确认）

- 同一个稳定风险事件默认只主动提醒一次；ETA 每分钟的小幅变化不能产生连续通知。
- 只有风险进入新的严重等级、出现新的重要事实，或用户主动选择“稍后提醒我”且到时风险仍存在，
  才允许再次主动提醒。
- “知道了，继续按这个计划”表示用户接受当前风险等级；同等级保持安静，但不永久关闭该类风险，
  风险明显升级后仍可提醒。
- 风险升级是状态变化，不采用“减少 X 分钟就提醒”的全局硬编码。`8 → 7` 分钟通常不是新事件；
  `8 → 1` 分钟或“换乘较紧 → 很可能错过固定班次”可以成为新事件。
- 固定提醒即使当前进度 unknown 仍可按预设时间触发；动态/实时推断因缺少进度而保持 unknown。
- 已过期的固定提醒不补发旧指令。设备在提醒时刻之后才恢复时，只依据当前新事实产生仍有意义的
  提醒。
- 目的相同的固定提醒和动态提醒去重，只保留实际已触发的关键提醒；不同目的的提醒不因此删除。
- 多个提醒同时出现时，优先显示时间窗口更明确、后果更严重的事项；通知正文只显示关键行动并将
  其他低优先级事项汇总为“还有 N 个待办”，进入 App 后再展示明细，不删除待办。
- 固定提醒可依赖本机通知；动态风险未来可依赖服务端 Worker + Push。这些都是 capability，不能
  承诺任何平台下 100% 到达。相关客户端、Push 与监控实现尚未完成。

## 9. 实际执行、延误与重规划

- Actual 已发生部分锁定，未来重规划不能改写过去；
- 偏离本身不是风险，影响受保护安排才形成风险；
- 延误不默认整天整体后移，先看当前缓冲/停留能否吸收；
- 一个地点可吸收时可建议具体缩短值；多个地点需释放时间时，系统应算出少量可行妥协方案，不把算术丢给用户；
- 用户可以拒绝所有方案自行调整；
- 错过具体服务后同时比较下一班/替代交通，Preview 后 Adopt；
- 当前实际位置作为重规划起点；若实际位置成为执行事实，可进入最终记录；
- 用户计划地点不能静默跳过，交通生成节点可随新路线替换。

提醒：
- 延误/明显偏离按稳定风险事件聚合提醒；
- 同一风险等级默认不重复催；只有严重等级升级、新重要事实或用户 snooze 到期且风险仍在才形成
  允许再次主动提醒的事件；
- 普通提醒 App 内；关键风险/需决策可系统通知 + App 内。

## 10. 跨日与时间显示

### 10.1 跨日关系
相邻 Day 可合法存在：
1. 同地点连续；
2. 交通本身跨日；
3. 用户接受未连接。

- 跨日地点/自由行动是同一连续节点，不拆成两份；
- 跨日交通按出发日→到达日连续记录；
- 不为了公式完整制造假节点/假时间。

### 10.2 时区
- 没有 Trip 级统一时区；
- 每个地点/事件按事件所在地当地时间展示；
- 底层保留时区与UTC；
- 跨时区航班轻提示“出发/到达均为当地时间”；其他普通行程不重复提示。

## 12. 费用 / 记账

### 12.1 定位
行程是主线，记账是辅助；不记费用不影响行程成立。

### 12.2 原始记录与汇总
- 原始金额/币种永久保留；
- 实际费用按消费发生日历史汇率快照换算；
- 用户切换基准货币后，历史旅行汇总按发生日历史汇率关系切换到新基准币，不用今天汇率重算过去消费；
- 没有可靠历史汇率就待换算，不编造。

### 12.3 计划费用 / 实际费用
- 两层都可选；
- 计划费用可按人计价或整笔计价；
- Trip 人数是默认人数，单笔计划费用可覆盖人数；
- 只有继承 Trip 默认人数的计划费用随 Trip 人数变化；
- 实际费用记录真实总金额，一旦发生不再随人数变化；
- 实际支付可由计划费用预填，但用户以真实付款修改；
- 退款/补差/手续费用正负新记录追加，不覆盖原记录。

### 12.4 汇总
- 当天只显示计划总数、实际总数；
- 整趟显示 Plan Total vs Actual Spent，并可看分类；
- 不做“当前预计总花费”；
- 预算系统暂缓。

## 13. 历史回顾与分享

### 13.1 历史回顾
旅行结束后从历史行程生成回顾视图，不要求用户额外证明旅行发生。回顾默认相信用户最终保留的
行程：即使没有定位、Actual 或 App 打开记录，只要内容一直保留到旅行结束，就默认属于该旅行。

只有存在明确事实时才排除内容：用户明确跳过、取消、删除/修正为未发生，或系统拥有可靠事实确认
未执行。缺少执行证据本身不是排除理由。

回顾默认极简，主线是地点、FreeAction/特别体验及实际或最终顺序；同一地点多次出现时保留多次。
普通步行、地铁、出租车和一般交通流水不进入回顾主线。交通本身属于旅行体验时（例如专程乘坐
观光列车），可以作为“体验内容”进入回顾，但不展示为底层 `TransportEdge` 日志。

历史行程允许用户在旅行结束后直接整理：补地点、标记没去、修正顺序、名称或备注，然后重新生成
回顾。回顾不是第二套独立事实数据库，而是历史行程源数据的展示结果；编辑历史行程不会重新启动
实时执行。

跨时区或国际日期变更线回顾始终按真实 timeline sequence / DayOccurrence 顺序显示，`localDate`
只是显示标签。允许 `1/10 东京 → 1/9 洛杉矶`，不能为了日期连续而重排，也不强制插入航班交通卡。

### 13.2 一键分享图片
用途：给人看。
- 一键生成整趟旅行一张长图；
- 顶部旅行标题；
- 按真实旅行顺序展示日期、地点与 FreeAction/特别体验；
- 旅行前/进行中：取当前有效计划；
- 旅行结束后：取用户最终保留并按明确排除事实修正后的历史行程；
- 可包含用户主动加入回顾的照片或简短文字（未来能力）；
- 默认不含交通细节、待办、风险提醒、订单、费用、私人备注和附件；
- 图片是带生成时间的静态快照，历史行程后续修改不会自动改变旧图片，用户需重新生成。

### 13.3 回顾分享链接

- 分享链接展示轻量回顾静态快照，允许未登录用户查看；只有执行“复制这趟旅行到自己的账号”时
  才要求登录。
- 分享链接默认长期有效，不再采用 7 天自动失效或成功复制即失效；用户可主动“停止分享”。
- 每次重新生成都是独立版本（如 v1/v2），不会自动关闭旧链接；用户可分别停止分享。
- 原历史行程后续修改不会更新已分享快照，需重新生成新版本。
- 默认分享旅行名称、日期、每天地点、FreeAction/特别体验，以及用户主动加入回顾的照片或简短
  文字（未来能力）；不分享交通细节、待办、风险提醒、订单、费用、私人备注或附件。

复制范围：
- 地点卡片；
- 自由行动；
- 地点与最终顺序形成的路线骨架；
- 原日期整体平移，尽量保留当地计划钟点；原 Actual 只作为参考，不成为新用户的事实；
- 不复制原用户费用、私人备注、订单、附件、待办或历史执行事实。

复制流程：
- 预览以 Day 1～Day N 为核心，不突出原作者绝对日期；
- 点击复制 → 选择新出发日期 + 确认/修改人数 + 确认/修改名称 → 创建 → 直接进入编辑页；
- 名称默认“原名称 copy”，重复复制为“copy 2 / copy 3 …”；
- 日期平移保留当地计划钟点；
- 日期相关客观事实重新校验；
- 中间空白 Day、跨日结构保留；
- 局部交通查不到或地点失效不阻止复制，标记待处理/已失效；
- 原行程不完整也可分享。

旅行结束后分享/复制：
- 取用户最终保留、并按明确排除事实修正后的历史路线骨架；
- 实际时间作为新计划参考；
- 实际时间缺失时可保留原计划钟点作为参考，但不能标成新用户 Actual；
- 普通交通不属于复制主线；交通本身是体验内容时按体验语义复制，不复制底层 Transport 历史。

自己“历史旅行复制为新旅行”与别人领取分享链接共用同一底层复制能力。

## 14. 网络、数据可靠性、保存与多设备

### 14.1 网络与供应商
- 无网络：产品采取硬失效态，不把旧缓存伪装成当前可靠界面；
- 网络恢复后先重同步关键数据再恢复正常界面；
- 单一供应商失败：只让对应能力失效，不让全 App 失效；地图、航班、铁路等 Provider 独立降级；
- 已确认计划事实可以显示，实时状态明确“当前未知”；
- 可靠备份供应商可自动接管，但不能为了有结果而降质量；
- 多个可靠来源冲突不做平均，按预设主来源并暴露冲突；
- Provider 失败时提供独立人工查询出口，例如航空公司/机场官网、公共交通运营商官网、Google Maps
  或 Apple Maps。外部跳转只帮助用户查询，不会让系统自动知道网页结果；没有结构化 Provider
  数据时，网页信息不能冒充系统事实；
- 核心 TRAVEL 后端不可用时明确显示服务暂时不可用，不把旧缓存伪装成当前可靠行程；V1 不把该
  场景设计为完整离线模式。

核心服务故障的用户托底是静态“行程图片备份”：

- 旅行前一天，或第一次进入“即将开始”的旅行时提醒一次用户保存当前行程图片，不每天重复；
- 图片可保存到相册或分享给同行人，必须显示生成时间，并说明后续修改不会同步到旧图片；
- 图片只用于应急参考，不是离线可编辑行程，也不能证明其中信息仍是最新事实。

### 14.2 自动保存
- 普通编辑自动保存，无常驻 Save；
- 显示 Saving / Saved；
- 持续失败明确 unsynced，不假装已保存；
- 自动重试少量次数；
- 离开时若仍有未保存失败编辑，提示重试/放弃；
- 多设备用乐观版本，不做 silent last-write-wins；
- 冲突时保留本地未同步编辑但不自动提交/合并。

### 14.3 Undo
- 重要编辑支持短时单步 Undo；
- 一个业务动作及其自动副作用作为一个原子动作一起撤销；
- 只保留最近一次，不做复杂历史。

## 15. 当前开发策略

现在已经具备进入 Backend Domain Blueprint 和领域引擎开发的条件。

建议顺序：
1. Domain model / 状态机 / 时间与约束模型；
2. 多方向排程引擎；
3. 冲突检测与 explainable reason/source；
4. Preview / Adopt 事务边界；
5. 自动化测试；
6. 薄测试 UI；

- 计算与采用彻底分开；
- 每个推导结果最好带 reason/source，能解释“为什么是这个时间/为什么冲突”；
- 冲突求解推荐策略独立成可替换/可迭代策略层，不写死进核心时间传播；
- 后续新增案例优先变成自动化测试。

## 16. 已确认边界内仍可迭代的实现细节

O-05/O-06 已确认产品规则：不设全局体验最低值或固定评分权重；用户明确最低时长才是硬约束；
候选必须解释取舍且不凑数；外部预约由用户处理并以“已调整”确认，不伪装商家官方确认。

体验展示语言、同级可行方案的比较实现、具体交互与更多真实案例仍可迭代，但不得重新引入全局
硬编码阈值、永久最便宜/最快优先级或虚假的外部确认。这些实现细节不阻止领域底座开始开发，
且必须集中在可演进策略层，而不是散落硬编码。

## 17. 已废弃 / 被替换的旧规则

以下不再作为开发依据：
- “整个日期区间不允许重叠，一碰到别的Trip就禁止” → 改为自然日唯一归属 + 合并/释放冲突；
- “日期全部过去后自动判未执行” → 未执行只能由用户确认；
- “必须有可靠执行证据才进入进行中” → 到开始日期默认进入进行中，监控另行启动；
- “当天执行开始 = 第一个地点离开时间” → 生命周期与实时监控拆开；
- “创建旅行必须填结束日期” → 只填开始日期，结束日期由行程推导；
- “无具体日期也可以先做 Day1～DayN 规划” → 创建必须有开始日期；
- “自定义地点必须有规范地址” → 名称 + 可定位位置即可；
- “交通生成节点分享时完全不复制” → 作为参考交通路径信息保留，但不锁死为正式地点；
- “分享都是链接/分享都是展示” → 一键分享图片给人看；行程分享链接给别人用；
- “分享链接一次性领取、7天过期” → 独立静态回顾快照默认长期有效，由用户主动停止；匿名可看，
  登录后才复制路线骨架；
- “行程分享复制任务/可复用任务” → 不复制任务/备注等，只复制行程骨架；
- “历史旅行通过改日期重新用” → 复制为新旅行；
- “拆分旅行” → 取消；
- “地点时间以开始+停留为唯一主要输入” → 到达/停留/离开三变量任意两个推第三个；
- “固定班次也需要用户手动锁时间” → 已采用固定班次天然为事实型时间锚点；
- “多个地点可压缩时只告诉用户缺多少时间” → 系统应生成少量具体可行妥协方案，用户选择；
- “用户拒绝推荐后继续动态弹新方案” → 用户拒绝/关闭后进入安静辅助，仅风险升级时重新提醒。

## 18. 本次已确认的新项目与首版架构条件

- 新建空白项目，不重构旧仓库，不迁移旧实际数据；新远程地址尚未指定。

- 后端领域优先，正式客户端后置；仅做必要的薄测试界面验证，不同时开发六个端。
- 多用户与数据隔离从首轮开始；管理员邀请开通，首版无公开注册。

- 同一账号可多设备登录，修改走服务端版本校验，不做最后写入覆盖。

- 单体模块化；Web/API与Worker独立进程，同一台主机Docker Compose运行。PostgreSQL保存业务数据；文件走对象存储。

## 20. 仍保留在完整蓝图的细则（不因首轮后置而丢失）

### 费用与人数
- 用户手工记账核心只有名称、金额、币种；不增加强制分类/备注/付款人表单。
- 日期默认来自当前记录上下文，补录以用户填写的消费/服务归属日期为准；支付日期和录入日期不覆盖行程归属日期。
- 具体节点关联只推荐，用户确认；不选就先按天，不强制挂地点。
- 用户主动选择币种永远优先；所在地仅用于预选，不按界面语言强行改变。跨国票据有明确计价币种时按该币种。
- 分类少而稳定：交通、住宿、餐饮、门票/活动、购物、其他；当天不做分类展开，整趟可看分类。
- 计划/实际分开，未实际记账不把预计当已花；实际与某计划费用的对应只推荐，由用户确认。
- 计划费用跟当前有效行程，失效预计退出当前计划合计；实际已花不因地点/交通删除而消失。删除归属节点时保留实际费用及必要说明，不级联删除真实支出。
- 退款直接负数记录，不维护到账状态；补差/手续费追加；用户可随时纠正或删除错误账目。
- 跨多晚酒店费用底层一笔，日汇总按已确认服务周期展示性分摊；计划按计划周期、实际按实际周期。跨日交通整笔归出发日。
- 按人计划费用可用Trip默认人数或单笔覆盖；人数变化不能改历史实际总金额。
- 预算、多人分摊、OCR小票识别留未来，不进入首轮。

### 记录与附件
- 最终一条时间轴保留地点执行状态（已执行/已跳过/未确认）；删除是编辑移除，跳过是执行结果，不混用。
- 未执行的原交通不占默认最终主线；实际交通未知显示未记录。此展示方式暂定，原交通仍可留后台历史。
- 自由行动的消费/备注不使其自动变成POI；只有用户主动转换，才变成普通地点或细化多个节点。
- 节点上的备注/待办/附件在记录整理阶段仍可编辑；旅行级附件可放签证/保险等，单附件一个主要归属，不做文件夹网盘。
- 所有附件有类型/数量/大小限制，具体数字后续工程阶段确定；默认不解析内容。
- 旅行回顾按真实 sequence 展示最终保留的地点、FreeAction/特别体验；没有 Actual 不自动排除。只有
  明确跳过、取消、删除/修正或可靠未执行事实才排除。普通交通、金额和状态不默认出现在极简回顾。

### 分享与删除
- 图片/分享链接是带生成时间的静态回顾快照；匿名可看，登录后才能复制路线骨架。链接默认长期
  有效，由用户主动停止分享；重新生成的新旧版本独立，不自动关闭旧链接。
- 复制创建新 Trip 需原子事务；日期归属冲突时不创建半成品。复制原日期整体平移并尽量保留当地
  时间，原 Actual 只作参考，不成为新旅行事实。
- 自定义地点按普通地点一起复制，不另加用户已拒绝的隐私弹窗；系统仍限制分享范围，不把私有附件/备注带出。
- 普通交通不进入回顾/复制主线；交通本身是旅行体验时按体验内容处理，不复制底层 Transport 日志。
- Trip永久删除前强警告，不输入名称二次验证；别人的独立副本不受影响。
- 不可逆合并不得伪装可Undo；无损合并保留来源、备注/任务/费用/附件，人数差异先由用户选默认人数。

这些规则分别纳入后续模块任务，不代表P0～P5自动授权开发全部功能。
