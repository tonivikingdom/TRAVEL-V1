## 2. 第一步：核对素材与提取契约

阅读仓库 AGENTS.md、当前适配器及其测试、环境配置和本包历史材料。报告读到的实际文件路径。
确认当前 Git 状态和基线；原分支已有成果时保留，不重新创建重复分支/PR。

先列明接口输入、成功/错误响应、必需/可空字段及校验条件，再实现服务。以原适配器源码和回归为当前 Travel 兼容性约束。

目标调用链：
Travel API → GoogleConsumerExperimentalRouteProvider → loopback HTTP sidecar → service-owned browser → Google Maps。

核心接口为 `POST /v1/transit/search`。请求包括 origin/destination 标签和坐标、date、time、timezone、timeMode。
成功响应的 provider、queryVerified、requestedQuery、fetchedAt、candidateCount、候选及分段形状均须通过未放宽的适配器解析。

历史材料没有给出完整实现；缺失代码允许新写。不能把文档摘要、手工回显请求或归一化 mock 当作已查询 Google 的证据。

## 3. 第二步：先做最小真实验证，不先搭一套大系统

先验证云端能运行受控匿名浏览器、访问目标页面并按可见 UI 设置查询条件。
在已获准的网络访问及适用使用范围内，选择一个日本公共交通起终点和可查询日期；记录明确的绝对日期、当地时刻和 IANA 时区。

优先验证同一个场景的 DEPART_AT 与 ARRIVE_BY；历史札幌站→小樽站可以作为起终点线索，但不得复用历史时间/票价/候选数充当新结果。

关键要求：
- 页面本身产生路线请求；不猜测、枚举或暴力探测私有接口。
- 记录实际选定的 UI 模式、日期时间/页面状态与收到的响应对应关系。
- 不自动信任第一条响应，不只靠“请求参数被回显”证明时间模式生效。
- 历史解析位置可指导调查，必须用当前观察确认；缺失字段保守返回 null 或明确拒绝，不能编造站点、车次、坐标、时间或票价。
- Schema guards 与查询语义验证分别可测，不能为了返回候选而关闭验证。
- 如遇 CAPTCHA、登录门槛、明确封禁或网络策略拒绝，停止相应 live 尝试并报告准确阶段；不做验证码绕过、代理轮换、指纹伪装或个人会话复制。

若 live 暂被阻塞，可继续不依赖外网的服务壳、契约、安全及合成回归；但停止追加 live 尝试，不重复靠更多合成用例冒充真实进展。交付明确标记 LIVE_BLOCKED / PARTIAL 及原因。
若观察证据可用，直接继续实现，不只交一份计划。

## 4. 第三步：实现兼容服务与最小保护

运行布局优先使后端和 sidecar 在同一云端网络命名空间中回环通信。
新服务只监听 `127.0.0.1`，默认关闭，受保护接口要求专用 Bearer 凭证；health 只报告状态，不启动浏览器、不访问 Google、不泄露凭证。

浏览器由服务持有，支持 Linux 环境的明确安装/启动配置，不硬编码 Windows Chrome 路径。
每次查询使用独立非持久化 BrowserContext/Page；不加载用户 Chrome 数据或登录会话。
单个 Google operation 并发；第二个请求明确 `429 BUSY`，不偷偷排队或无限重试。
处理超时、取消、页面/上下文回收及浏览器异常，避免进程和内存泄漏。

保留细分错误：参数无效、未鉴权、模式未开放、服务关闭、BUSY、浏览器不可用、超时、上游受限、请求不匹配、结构变化、确证无路线。
“无路线”只能来自符合请求且明确为空的结果，不能作为网络或解析错误的通用兜底。

缓存若实现，应短期、内存、有界，键包含所有影响结果的查询条件和 timeMode/timezone；缓存命中保留真实获取时刻，不伪造为新查询。具体 TTL 记录为新实现决策，不冒充已恢复的旧值。

源码位置优先隔离在 `services/google-consumer-transit/`。可添加为运行/测试该服务确需的 workspace 配置和锁文件变更；逐项说明，不批量升级无关依赖。不得改 schema/migration 或顺带放宽原 CI。

## 5. 本批功能范围

目标恢复 Travel 当前 HTTP 适配器消费的 **DEPART_AT + ARRIVE_BY 直接查询**。
分别实现、分别测试和分别报告支持状态；某种模式尚未核实时明确返回不支持，不静默转换成另一模式。

本批不实现 URL 反向导入、不做 NOW/立即出发、不做 LAST_TRANSIT/末班车。
这是对新实现首批范围的明确限制，不是删除或否认原本地工具的已有能力，也不得声称新实现已完整替代原工具所有入口。
如保留 import 路由壳，应明确返回未支持，不给假结果。

DEPART_AT 验证实际出发不早于请求；ARRIVE_BY 验证实际到达不晚于请求，并明确日期/跨日处理。
以绝对时刻进行前后衔接校验，所在地时区用于输入转换和显示。
不对候选顺序作未经证明的保证，不按历史固定候选数或票价验收。

## 6. 测试与证据

先运行现有适配器及相关基线回归，新增以下测试：
- HTTP auth/disabled/unsupported/BUSY/timeout/cancel/error mapping。
- 请求回显不同、时区不同、日期无效、时间模式混淆、错的首响应与后续正确响应。
- 结构缺失/变更、可空票价/可选字段、站点关系与坐标连续性。
- DEPART_AT、ARRIVE_BY 独立语义；跨日/时区、候选时间越界。
- 缓存模式隔离、时间来源、请求结束后资源和并发锁回收。

必须区分四层结论：
1. 新服务单测/契约测试通过。
2. 浏览器在云端实际运行。
3. 真实 Google 查询与解析通过。
4. Travel API/真实 HTTP/PostgreSQL 联调通过。

不能用 1 代替 3，不能用 3 代替 4。
真实验证成功后，以低频查询验证一条较简单铁路路线与一条公交/铁路/步行混合路线；若没有可靠新数据，报告缺口，不补造。
在隔离测试账户和行程运行真实 HTTP/持久化链，验证 Query 后的 Snapshot/Preview/显式 Adopt/Undo；界面不在本任务范围内。
后续 Preview/Adopt/Undo 不应再次查询 Google，不能自动采用候选。

取得新证据时只保存允许的脱敏摘要和明确标注的测试样本；不提交完整 Google URL/pb、headers、原始响应、Cookie、密钥、个人浏览器数据。
