## 1. V1 的目标与主流程

V1 是一个以个人真实旅行使用为中心的旅行助手，让用户方便地整理行程、查看每天安排、管理交通和航班，并在旅行中得到必要的变化提醒和重新规划入口。

V1 不扩展为综合交通运营平台、自动调度系统、GIS tracking platform、workflow engine、full travel ERP 或 Provider aggregation platform。

正式主流程固定为：

创建旅行 → 安排每天地点/活动 → 设置交通 → 查看/选择路线 → 查看航班 → 出行 → 收到必要提醒 → 必要时重新规划。

每个新产品任务必须回答 **Which V1 user flow does this improve?**，并指出具体改善的用户任务。无法回答时默认 **DEFERRED**。不再用“后端还有什么没做”决定下一步。

P0–P5 + P5E2 已形成充分的 backend foundation。新的优先级为：

usable product > simple interaction > real-world validation > additional infrastructure completeness。

这不等于真实 Provider、正式客户端或生产环境已可用，也不授权下一阶段施工。

## 2. 产品简单性契约

| 原则        | 正式约束                                                         |
| ----------- | ---------------------------------------------------------------- |
| P-SIMPLE-01 | 工程边界可以细，用户流程必须粗。                                 |
| P-SIMPLE-02 | 内部状态机不得直接成为用户操作步骤。                             |
| P-SIMPLE-03 | 系统解释问题，不要求用户理解实现。                               |
| P-SIMPLE-04 | 默认只显示当前需要处理的信息。                                   |
| P-SIMPLE-05 | 高级能力只有真实需求触发后才继续开发。                           |
| P-SIMPLE-06 | 已经实现但暂时不需要的能力：保留而不是删除，冻结而不是继续扩展。 |

Backend may be strict and complex so that the user experience can remain simple.

保留现有并发 fencing、immutable evidence、execution history、Provider ACTUAL protection、Undo audit、route topology validation、ownership isolation、idempotency 和 migration safety；不以简化产品为由回滚这些保护。

禁止仅因“未来可能需要”新增 Provider abstraction、state machine、table、enum、webhook layer、scheduler、notification channel、storage provider 或 permission hierarchy。必须先有明确的 V1 use case，再单独授权实现。

## 3. 正式用户概念与内部词汇

默认产品界面只围绕：**旅行、日期、地点 / 活动、交通、航班、提醒**。

产品语言可以使用“当前路线”“新的路线”“重新规划”“使用这条路线”“撤销刚才的修改”“航班有变化”“可能赶不上”。

以下术语只用于 Domain、Application、Persistence、Debug、Logs、Tests 与 Admin/developer diagnostics，不进入普通用户主流程：

`CandidateSnapshot`、`RoutePreview`、`AdoptedRoute`、`RouteAdoptDelta`、`OperationReceipt`、`ExternalExecutionOrigin`、`GroundTransitLegExecution`、`GroundTransitObservation`、`GroundTransitStateTransition`、`ExecutionFrontier`、`AssistanceCapability`、`ProviderHubRef`、`anchorFromNodeId`、`FULL_CORRIDOR`、`SUFFIX`、`EXTERNAL_ORIGIN`、`R1 / R2`。

工程文档可以继续准确使用这些术语。正式 UI 不把它们转成用户需要学习或逐项操作的概念。

## 4. 路线、重新规划与用户选择

内部保留 Query → CandidateSnapshot → Preview → Adopt。产品表现为：

搜索路线 → 显示路线方案 → 用户点击“使用这条路线”。

Preview 是系统保护层，不是用户概念。一次路线变化，正式 UI 最多要求 **1 次查看 + 1 次确认**；Handoff、Query、Preview、Adopt 由内部 pipeline 承担，不要求用户依次操作。

异常时可以显示：“当前路线可能无法继续。从你现在的位置重新规划？”随后提供“查看新路线”和“使用这条路线”。只有服务器已验证安全执行起点时才能使用“你现在的位置”；起点未确认时应说明无法判断，并使用已有明确确认流程。不得向用户暴露 E、divergence、suffix、anchor、retained prefix 或 materialization。

系统计算事实与后果，用户做选择。V1 允许自动更新事实、更新 ETA、计算风险、判断路线可能不可行、生成候选和提示用户；禁止自动切换路线、采用新路线、删除用户选择、修改独立时间要求或产生新的费用承诺。

“允许生成候选”是产品权限边界，不是本批的功能授权。现有路线搜索仍由用户明确触发；automatic Query、automatic Preview、automatic Adopt 均冻结且未启用。正式 UI 的粗粒度操作只包装已授权 pipeline，不引入无用户触发的自动调用。

## 5. 撤销与风险语言

保留 Undo，正式 UI 只表达“撤销刚才的路线修改”。不展示 receipt、delta、route version、archive restoration 或 historical anchor。

路线已产生真实执行证据而无法 Undo 时，可以显示：“这条路线已经开始执行，无法直接撤销。可以重新规划后续行程。”不得删除执行历史来让撤销成功。

| 内部语义示例                  | 产品语言示例             |
| ----------------------------- | ------------------------ |
| `BUFFER_BELOW_SYSTEM_MINIMUM` | 换乘时间可能不够         |
| `PROTECTED_TIME_INFEASIBLE`   | 按当前预计时间可能赶不上 |
| 信息不足，无法可靠判断        | 目前无法判断是否来得及   |

严格时间模型继续保留。用户只表达“我计划几点”“最晚几点”“最早几点”“至少停留多久”；系统内部映射 TemporalLayer、TemporalSourceKind、UserTimeIntent 和 constraint propagation，默认界面不暴露这些实现。

## 8. 正式 UI surface 与渐进展示

Debug Web 继续是工程测试台，可暴露内部结构。正式客户端另开 UI surface，不把 Debug Web 直接演变为正式 Desktop UI。

正式信息架构优先压缩为：

旅行列表 → 旅行详情（日程 / 交通 / 提醒）。航班作为交通中的重要特殊类型。

不为 execution、monitoring、external origin、risk engine 或 Provider 建一级用户导航。

每个正式页面都必须问：“用户为了完成实际旅行任务，需要知道这个字段吗？”只有明确 YES 才进入默认界面；其余默认隐藏，必要时放入更多信息、debug 或 developer diagnostics。

默认界面 simple。正常路线不显示重新规划、execution origin 或 route replacement details；路线异常时再显示“路线有变化”“查看替代方案”。

Desktop 与 Mobile 分别设计布局，共享 API、Domain、data model、Design Tokens 与 SVG icon set，不强制相同布局。遵守现有视觉要求：visible content 整体视觉居中；icon + text 作为一个整体居中；左右 padding 对称；card/button/badge/empty-state 尺寸变化时重新计算视觉中心。

## 9. 下一阶段与授权范围

下一推荐阶段：**P6A — Formal V1 User Experience Foundation**。目标是把现有能力变成真正能日常使用的产品，优先验证真实用户主流程。

首版 surface 仅包括旅行列表、旅行详情、Day itinerary、Place / FreeAction editing、Transport summary、Flight summary 与 Notifications。Route/replanning 复杂操作通过最小入口接入，不一次把全部 P5 backend 能力做成 UI。

本 boundary PR 合并后，P6A 仍须单独授权、明确客户端 surface 与真实验收；本批不开始 P6A。
