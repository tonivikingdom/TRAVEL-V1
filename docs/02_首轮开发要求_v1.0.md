# 首轮开发要求 v1.0｜新建空白项目

## 1. 本次目标
从空白项目建立一个**可测试、可解释、可迁移、多终端共用**的旅行后端。用户是首次开发软件的新手；需要中文、简明、可操作的阶段反馈，不能让他自己排查一大堆未说明的工程问题。

完整产品愿景维持不变：根据用户需求规划合适旅程，辅助执行与临时调整，减少繁琐操作，留下真实记录。但首轮只做支撑这些能力的必要内核，不一次做完产品。

## 2. 项目与仓库前提（不可忽略）
- 这是Greenfield空白项目；不要克隆、复用或修改旧业务仓库作为默认起点。
- 使用用户确认的新项目目录和新GitHub远程。地址未给时，禁止猜测。
- 先检查目录、Git、origin、分支、工具环境；有未知文件不得清空。
- 若用户仅提供空目录，可在其中初始化本地骨架；缺失远程/基线时记录发布阻塞，不得伪报已push/PR。
- 新远程没有main首提交时，要求用户先建立最小基线或单独授权初始化；没有“无条件直推main”的例外。

## 3. 建议技术基线（工程选择，不是旧项目事实）
- TypeScript strict；Node.js 24 LTS作为本次建议大版本，开工核验支持状态与兼容性。[S04]
- pnpm workspace（锁定具体版本）、模块化单体，不上微服务/Kubernetes。
- 轻量HTTP API框架优先Fastify；数据库PostgreSQL；ORM优先Prisma。P0核验相互兼容版本，写ADR和lockfile；不在本包猜具体补丁号。
- 建议测试框架Vitest；HTTP契约与领域测试分层；真实PostgreSQL集成测试不能以SQLite代替。
- Web/API和Worker两个运行入口，共享domain/application packages；同机Docker Compose。[S05]
- ObjectStorage接口；本地测试可用实现该契约的磁盘后端，文件在隔离volume，不塞数据库；云S3兼容实现以后替换。
- 首轮不锁定Electron/Tauri/React Native/Flutter/Swift/Kotlin。正式双端UI与原生框架后续单独选型。

## 4. 目录边界提案
```text
apps/
  api/                  # HTTP、鉴权入口、DTO映射
  worker/               # 持久任务执行入口
  debug-web/            # P5才实现，测试台不是正式产品UI
packages/
  domain/               # 纯时间/约束/邻接/冲突规则
  application/          # 用例编排、权限、事务边界
  contracts/            # 平台无关请求/响应/错误码
  persistence/          # PostgreSQL/ORM/事务适配
  providers/            # 地点/交通/航班/汇率接口与适配
  storage/              # 对象存储契约/本地测试实现
  test-fixtures/        # 明确标记虚构的测试样本
infra/compose/          # dev/staging独立配置与卷
prisma/migrations/      # 确认采用Prisma后创建
scripts/
docs/
```
只创建本阶段真正需要的包；不为表面架构完整建几十个空服务。

## 5. 首轮阶段与授权边界
| 阶段 | 主要交付 | 不做 | 推荐模型 / 强度 |
|---|---|---|---|
| **P0 首次任务** | 架构蓝图、规则登记、workspace、API/Worker健康骨架、Compose、CI、最小smoke测试 | 完整登录、复杂业务表、真实外部Provider、正式UI | **GPT-5.6 Sol / Extra High（xhigh）**；备选Luna / Max |
| P1 基础安全与任务 | 邀请/Magic Link/会话撤销、账号隔离、持久任务、存储契约、dev/staging | 协作、公开注册、订单系统 | Sol / Extra High；明确子任务可Luna / Max |
| P2 行程领域 | Trip/Day/Visit/Transport骨架、邻接失效、版本、基础生命周期与三层时间数据 | 未决日边界自动处理、旅行拆分 | Sol / Extra High |
| P3 纯计算内核 | 正反双向传播、来源解释、约束/缓冲冲突、固定夹具测试 | 全网路线、体验质量评分硬编码 | Sol / Extra High；疑难用Max复核 |
| P4 查询与采用 | Provider契约探针、候选、Preview/Adopt、乐观锁/幂等/撤销、受控推荐策略 | 擅自订票/改签/改预约 | Sol / Extra High |
| P5 内测验证 | 最小调试界面、站内通知、已确认流程的端到端验收、部署说明 | 正式设计、原生包装/Push | Luna / Max实施；Sol / Extra High审查 |

这些推荐是针对任务风险的工程判断，不是模型质量保证。可用性和强度以实际Codex版本为准，详见模型文档。

**每阶段独立分支和PR。P0完成停住；未获确认不能自动执行P1。** P2之后的详细任务在前一阶段真实代码基础上复核再发，不照纸面臆测路径。

## 6. 当前必须实现/预留/后置
### 必须从基础阶段做对
多用户隔离；长期可撤销会话；服务端时间/版本/授权；数据不编；Preview不改行程；采用原子性；真实记录保护；错误可解释；任务落数据库；开发环境隔离；GitHub可追溯。

### 建接口/边界，不等于实现完整功能
位置证据输入、NotificationEvent、Provider、ObjectStorage、RecommendationPolicy、未来客户端凭证方案、集中授权函数。

### 不在本轮批量开发
正式Web/桌面/移动界面；Windows/macOS安装包；iOS/Android应用；原生推送、后台定位采集；同行协作；公众注册；天气；预算；票据订单管理；OCR/附件解析；多人分摊；分享长图与一次性领取完整UI；无损Trip合并完整交互；跨天推荐；完整审计和自动异地灾备。

费用、附件、待办、分享、合并的**完整产品规则仍保留**，不因本轮后置而删除；P1/P2只建必要的可扩展边界，不提前铺全部业务接口。

## 7. P0验收清单
- 新项目位置、origin和分支已明确；若远程未配置须标BLOCKED。
- 架构蓝图列出不可变事实、用户意图、计算结果的区分；未决项不写成已确认。
- 能安装锁定依赖、lint、typecheck、unit test、build。
- API提供liveness/readiness；readiness区分DB依赖，不能总返回ok。
- Worker独立启动、优雅停止和健康心跳；此阶段没有业务任务时不得宣称后台通知已完成。
- Compose启动API、Worker、PostgreSQL；重启普通容器不丢命名卷内测试数据。
- P0不开放业务API给外部；测试服务默认绑定本机。
- Dev/Staging环境模板不含真实密钥；生产配置默认禁用、不自动部署。
- CI真实执行可执行的检查；数据库测试若暂未存在应如实标未实现，不以空测试套件“绿灯”。
- 文件变更分组提交，push分支，PR存在；报告真实链接、SHA和测试证据。

## 8. 首轮能力限制必须写在测试界面/说明中
- 本轮没有原生Push，不保证App关闭后的关键通知触达；站内提醒不是锁屏通知的替代品。
- 没有移动端定位采集时，只能使用标明来源的测试/用户主动输入证据；服务器不能凭空获取用户位置。
- 无真实Provider凭证/覆盖时，接口返回UNAVAILABLE或只运行明确标记的fixtures，不展示虚假生产交通。
- 测试期间接受数据重置，不意味着正式可用；允许重置仅限隔离测试库，必须明确环境并保护其他数据。

## 9. 停止条件
遇到仓库目标不明、权限不足、密钥缺失、产品边界矛盾或无法运行关键测试：完成不受影响部分，列明BLOCKED项，停止对应实现。不能为了交付自行取消鉴权、把假数据放生产或绕过用户选择权。
