## 实现边界

- `ExecutionRisk` 是独立于 `NotificationEvent` 的 owner/Trip 私有持久状态；保存稳定 fingerprint、kind、
  severity、来源/受保护目标、证据引用、首次/最近发现、acknowledge、snooze、resolved 与评估版本。
- evaluator 是纯确定性计算，只读取现有 `PLANNED / ESTIMATED / ACTUAL`、UserTimeIntent、
  SystemDwellSuggestion 和已知 Buffer 证据。时间事实优先级保持 `ACTUAL > ESTIMATED > PLANNED`；
  evaluator 不写 TemporalValue，不覆盖 ACTUAL，也不增加 Trip version。
- 首版 protected anchor 包括 fixed-service Transport 的 PLANNED departure、任意 Transport 的 ACTUAL
  departure，以及用户明确的 EXACT / NOT_AFTER point-time 要求。普通 non-fixed selected Transport 仍是
  P5C current-plan anchor，但不会仅因已选择就升级成 protected commitment。
- 从当前可靠执行证据只寻找最近的 downstream protected target。没有 protected target 时保持安静；缺少
  关键证据时输出 `UNKNOWN_EXECUTION_MARGIN`，不把 unknown 判成 safe。
- 已知到达压缩用户 MIN_DWELL 或系统建议时产生可执行风险；晚于固定班次时产生
  `FIXED_SERVICE_MISSED / INFEASIBLE`，并只返回 `requiresRouteReevaluation=true`，不猜下一班。

## 生命周期、抑制与并发

- 生命周期为 `OPEN / ACKNOWLEDGED / SNOOZED / RESOLVED`。acknowledge 只让同等级通知保持安静，
  不修改要求或事实；snooze 固定 15 分钟。
- 相同 protected target 在 unknown、可执行风险和 infeasible 间共享 fingerprint；严重度升级、snooze 到期
  且风险仍存在时可以产生新通知。同风险同等级普通重评不重复通知。
- resolved 后重现会创建新的 lifecycle generation。Notification dedupe key 使用
  `execution-risk:<risk-id>:<severity>:<notification-generation>`，不是随机业务身份。
- reconcile、acknowledge、snooze 共用 owner advisory transaction lock 和 Trip row lock；数据库 partial
  unique index 保证同 owner/Trip/fingerprint 最多一个 active generation。风险与通知在同一事务写入。

## API 与 Debug Web

- `POST /trips/:tripId/execution/evaluate`
- `GET /trips/:tripId/execution/risks`
- `POST /trips/:tripId/execution/risks/:riskId/acknowledge`
- `POST /trips/:tripId/execution/risks/:riskId/snooze`

所有接口严格 owner scoped，ADMIN 没有跨 owner 例外。Debug Web 只增加手工触发、列表、acknowledge 和
snooze 的开发测试入口；没有后台轮询、正式颜色规范或产品 UI。
