## 1. 产品目标：帮用户旅行，不让用户维护系统

> 用户决定想去哪里、怎样取舍；系统帮助组织行程、计算时间、连接交通、找出重要影响，让出行时少找资料、少做重复操作，并自然留下记录。

产品同时服务安排、出行、临时调整、回顾。不能为了简单而退化成纯行程表，也不能为了完整而变成交通运营平台或执行监督系统。

默认用户心智：

> 我要去这些地方 → 排一下顺序 → 这几个时间很重要 → 系统帮我算其余部分 → 有问题告诉我 → 我决定怎么改。

每项设计都须回答：**具体替用户少做了什么，或者避免了什么重要损失？** 只让架构更完整、却不改善当前任务的扩展默认后置。这个价值判断是后续设计基线，尚未经过真实使用数据验证，必须通过完整场景试用校准。

安全、数据真实性和用户选择权是底线，不参与“为了更快上线可以牺牲”的排序。

## 2. 已开发能力：保留并复用，不继续无目的扩张

现有事实：保留认证、权限隔离、时间事实分层、版本校验、事务、幂等、历史保护、监控、风险、路线替换、执行起点验证、Adopt/Undo 和 storage reconciliation。P0–P5 + P5E2 已形成 backend foundation，P5E2 与 P5 Audit Repair F-07/F-08 已完成；这不证明正式产品可用。

Backend may be strict and complex so that the user experience can remain simple.

内部结构不成为普通用户菜单或操作步骤。正式用户概念围绕旅行、日期、地点/活动、交通、航班、提醒，使用“当前路线”“使用这条路线”“撤销刚才的修改”等自然语言。

`CandidateSnapshot`、`RoutePreview`、`AdoptedRoute`、`RouteAdoptDelta`、`OperationReceipt`、`ExternalExecutionOrigin`、`GroundTransitLegExecution`、`GroundTransitObservation`、`GroundTransitStateTransition`、`ExecutionFrontier`、`AssistanceCapability`、`ProviderHubRef`、`anchorFromNodeId`、`FULL_CORRIDOR`、`SUFFIX`、`EXTERNAL_ORIGIN`、`R1 / R2` 保留在工程、Debug、日志、测试及诊断中，不要求普通用户理解。

## 3. 四段用户旅程（产品目标）

### 3.1 行前：把想去的地方安排好

添加地点或自由行动，调整顺序与日期，填写重要时间和必要停留，查看交通方案。先形成可用行程，不要求一次填完整。

沿用当前创建要求：旅行名称、开始日期、人数；人数可有默认值，不新增强制结束日期、国家或完整预订资料。不引入无日期 Trip，不改变日期唯一归属。

正式添加地点使用名称、地址、地图选点等入口，不以手填经纬度为主要流程。自定义地点仍需可定位依据；地址未知不编造，接入方式由具体任务按 Provider 能力确定。

可以只确定“下午必须到车站”，上午保留自由行动；可推导时间不重复填，未知内容不因空白被当作错误。

### 3.2 旅中：打开手机知道下一步

优先显示今天、按计划的下一步、选定交通时间及上下车地点、今晚住宿和对应导航/资料入口。

无可靠用户执行证据时，只说“按计划接下来……”，不说“你现在已经到了……”。不开定位、不逐站打卡仍可浏览行程、资料并做受支持的手工编辑。

桌面偏编排，手机偏查看和现场操作；共享业务与设计资源，分别布局，不把宽屏表格压缩成手机界面。

### 3.3 临时调整：说明影响，给少量可靠办法

延长停留、跳过地点或交通变化时，先解释重要安排的影响，再给少量有可靠依据的方案。优先局部最小改动，不默认整天后移；比较到达时间、费用差异、停留损失和风险，不只追求数学可行。

用户可拒绝并保留选择；冲突继续真实显示，不反复弹窗强迫接受。信息不足时提供外部查询或已支持的手工调整，不编造替代班次。

### 3.4 旅后：自然留下记录，不补作业

保留最终行程和已有事实，未来可通过明确记录整理入口修正。没有 Actual 不等于没有旅行，没有定位不等于没去地点。

不要求补每站到达/离开，不考核记录完整率；轻量历史查看优先于轨迹、自动日志或复杂分享平台。本轮不改 Trip/capability 生命周期及事实修正规则，改善历史整理另开任务。

## 4. 功能优先级与首版做法（目标，不是实现清单）

| 能力                   | 用户价值                 | 首版边界                                                            |
| ---------------------- | ------------------------ | ------------------------------------------------------------------- |
| 今日与下一步           | 现场马上找到该做什么     | 顺序、重要交通、酒店、导航、资料；未知位置不伪装实时位置。          |
| 自由编排地点/活动      | 减少填表，保留自由度     | 添加、排序、跨日移动、自由行动、关键时间，不要求全部配齐。          |
| 真实交通与外部地图入口 | 减少重复查询和抄写       | 指定日期/出发/到达条件、换乘、票价、选择方案；能力不足明确说明。    |
| 时间重算与冲突解释     | 替用户算时间账           | 目标与结果、重要后果及局部改法，不篡改独立约束。                    |
| 航班与固定安排         | 易查重要行程，减少遗漏   | 搜索/绑定或现有受支持入口、事实更新、关键变化，不订票改签。         |
| 关键提醒               | 需要行动时有帮助         | 安静、相关、可操作；保留去重/停止边界，不等于锁屏送达。             |
| 轻量资料               | 快速找酒店、票、预约信息 | 先备注/链接，少量图片/PDF经对应存储与隐私验收后接入，不做订单系统。 |
| 静态行程备份           | 故障时应急参考           | 带生成时间的日程图，可保存/分享，不是实时离线行程。                 |
| 待办、费用、回顾、复制 | 辅助整理与复用           | 逐项做薄，保持可选，不阻塞主流程。                                  |

每次实现先区分 **可直接复用 / 需要薄适配 / 需要新能力**。优先目标不表示接口齐备，也不授权真实付费服务。

末班车查询有旅行价值，但只在数据与语义可靠时开放；不把普通候选或估计冒充末班车，也不为此先造全量交通数据库。

## 5. 同一份行程，按场景呈现

同一套行程事实，不新建“计划数据”“今天数据”两套需同步的业务真相。

建议从旅行入口进入详情，切换“今天 / 全部日程”；交通、航班、资料附在对应安排上，提醒有明确入口并能返回相关行程。不为风险引擎、监控、执行起点、Provider 建一级导航。

行前优先编排，旅中优先查看；不改变 Trip 生命周期，不要求频繁切换“开始/完成”。主行程以用户地点和自由行动为主，换乘细节默认折叠在交通摘要，临近换乘或展开时突出站台、步行、上下车；底层节点与历史不删除。

当前最相关时间优先，不默认每卡并排三层。但“要求19:30前到 / 当前预计19:56”不能合并；计划、预计、实际可辨，估计不冒充事实。按事件所在地当地时间显示，跨时区明确提示；地址、班次、时区、当前位置无证据不猜。

按钮、徽章、卡片、空状态的可见内容组视觉居中，icon + text 整体居中、左右留白平衡，尺寸变化重新布局；正文与需快速扫描的行程按可读性对齐，视觉居中不等于所有段落居中。Desktop/Mobile 共享 API、Domain、data model、Design Tokens、SVG icon set，分别实现布局。

Debug Web 仍是工程测试台，正式客户端另开 surface，不直接把测试台演变为正式 Desktop UI。

## 6. 自动化分三层

### A. 帮用户算：产品核心

保存编辑、计算停留和时间缺口、检查重要冲突、在授权范围刷新既有方案估计/运行事实，应减少操作。计算不意味着重写独立时间要求、移动地点或替换交通；现有显式入口与权限先保持，本轮不改运行行为。

### B. 帮用户找：保留价值，受控交付

点击“搜索路线”“看看怎么调整”后，Query、Snapshot、Preview 可在同一个用户动作授权范围内部串联，不要求逐个点击工程按钮。

时间变化/风险触发的后台候选准备是保留方向，不永久冻结；**当前未启用的自动 Query/Preview 仍未启用**。开放须逐场景明确触发、去抖/去重、缓存、请求上限、费用限制、取消、过期处理与用户停止规则，单独授权测试。

不预建通用推荐平台，优先复用可靠候选和确定性规则；一个主建议、最多两个可靠备选，不凑数。

### C. 替用户做决定：不得静默执行

改变路线/班次、跳过用户地点、修改预约、压缩明确受保护安排或产生费用承诺，都须看清后果后明确选择。接受某次风险不永久授权后续自动采用。自动 Adopt 不因受控查询方向而获得授权。

## 7. 简化交互，不削弱知情与起点校验

取消所有重规划“最多1次查看+1次确认”的硬上限，改为最少必要操作、工程步骤内部化；必要真实决策不省略。

通常“看方案 → 使用这条路线”即可；起点未知须先用现有合法方式确认，费用/重要影响须在最终确认前展示。不得跳过这些条件以减少点击。

正常路线不主动弹重规划，但交通详情保留用户主动更换路线入口，不以系统风险为必要前提。外部地图只帮助查询，不授权任意 GPS 重规划，也不把外部页面变成已核验事实。

## 8. 提醒、定位与撤销要说真话

重点是变化影响什么、现在能做什么，不是监督用户按计划执行。正常漂移无后果时静默更新，相同已接受风险不反复催，不用密集打卡维持完整性。

现有服务端 Flight/Ground Transit monitoring、站内 NotificationEvent 与原生 Push、客户端后台定位不同。Push 有潜在旅中价值，当前投递能力后置且未实现；未验证前不承诺锁屏/App关闭后的送达。固定提醒也不能因只有日期字段就宣称可用。

定位按需且需授权；起点证据规则继续执行。Provider 车辆事实不是用户位置，GPS sample 不自动获得记录许可。

### Undo 待专项复议，现有守卫不变

Provider 查到新信息与用户本人已执行是两件事。现有外部路线 Undo 可能因后台新 observation/state transition 而拒绝，即使没有 TransportEdge ACTUAL；本轮保留该守卫和历史保护，不改实现。

产品不得统一解释为“你已经开始执行”。无法取得更细原因时，使用“相关状态已更新，当前无法直接撤销；需要重新检查后再调整”。只有确有用户执行依据，才能说已开始执行。

后续专项评估：保留全部监控历史时能否安全撤回未执行规划，或提供重新选择旧方案入口。放宽前须证明事实保护和回归，不通过文案 PR 改守卫。

风险 enum 映射自然语言，如“换乘时间可能不够”“按当前预计时间可能赶不上”“目前无法判断是否来得及”；不暴露内部错误与审计术语。

## 9. 轻量辅助与明确后置

资料先名称/备注/链接，图片/PDF按存储能力开放；不从“已订”备注或凭证图推导官方确认，不强求订单号或完整预订流程。

静态备份保留原定应急方案，显示生成时间与“后续修改不会同步到旧图片”。公开分享与个人备份采用不同内容白名单，默认不意外带出私人备注、凭证等敏感信息。

待办为标题、状态、备注、可选提醒；费用为可选名称/金额/币种，保留原始记录，不记不影响行程；回顾看最终行程；复制复用地点与顺序，重新核验班次/日期信息。

完整预算、多人分摊、OCR、轨迹日志、分享版本平台后置。不无需求扩展逐站强制确认、GPS完整率、车上/站间/任意坐标通用重规划、万能Undo/Redo、订单/自动改签、通用供应商聚合、协作/权限矩阵、复杂运营后台或同时六端原生包装。

保留认证隔离与个人使用优先；Admin 限于邀请、启用/禁用账号和必要管理，不以本轮授权查看他人活动或建设运营分析。

## 10. Provider 验证缩到实际使用范围，不绕过闸门

F-05/F-06 **OPEN**；没有具体任务时 **未排期**，不关闭、不把验证推到真实使用之后。准备使用 Provider X / account-plan Y 时，验证本次所需字段、留存/存储、归因、删除、额度/费用、覆盖及账户权限；公共文档不足以证明 entitlement。

保留已确认 **R7：供应商 Push/Webhook 优先、Polling 补充、Query 按需**。具体供应商是否支持、账号可用性、认证、投递保证、重放/顺序、失联补拉和 polling fallback 仍需实际证据。供应商 webhook 与手机原生 Push 不是同一能力；不预建无具体场景的通用 webhook abstraction。

先让一个可靠来源服务一个实际交通/航班场景，不先造全量治理平台。实验 sidecar、synthetic fixture、正式 Provider 明确区分。

UI 与真实数据验证可围绕同场景并行；合成数据仅用于明确标记的开发验收。正式出行使用前过对应真实数据闸门，缺失来源受控降级，不拖垮基础编辑、不以假数据补齐。真实/付费接入与部署仍需独立授权。

## 11. 本轮不改的规则与草案变更表

账号隔离、日期唯一归属、Trip/capability 生命周期、计划/预计/实际分层、用户意图、执行起点、实际事实/历史保护、Adopt/Undo守卫及无网/核心故障策略不变。

当前无网不显示缓存行程、不支持离线编辑；静态图片是独立应急资料，不引入离线缓存。单 Provider 故障局部降级。先用现有能力完成用户流程，再对妨碍使用的具体规则提出可验证专项变更。
