# 旅途计划｜多方向排程与冲突求解 V0.2 开发基线
版本日期：2026-09-17  
状态：可开始实现 / 推荐策略持续迭代

## 1. 一句话定义
排程引擎不是单向时间计算器，而是一个可以从头、尾或任意中间锚点双向传播的约束图：真实交通通过查询获得，用户意图作为约束保留，冲突通过“计算候选解 → Preview → Adopt”处理。

## 2. 基础变量
普通地点至少有：
- plannedArrival
- plannedDeparture
- plannedDwell
- estimatedArrival / estimatedDeparture / estimatedDwell
- actualArrival / actualDeparture / actualDwell

三变量关系：arrival + dwell = departure。任意两个可推第三个。

每个 Planned 值必须能解释来源：
- USER_VALUE
- USER_CONSTRAINT
- ADOPTED_TRANSPORT_FACT
- SYSTEM_SUGGESTION
- DERIVED

建议进一步保存 reason/sourceRefs，避免只有数字没有原因。

## 3. 两类锚点
### 3.1 事实型锚点
由已采用的真实服务/预约事实给出，例如 G93 20:21 发车。改变它必须改变所采用的服务。

### 3.2 用户型约束
例如：
- 最晚23:30到浦东；
- 南京南至少留40分钟；
- 19:00必须到餐厅。

用户约束与当前方案结果同时保留，不能互相覆盖。

## 4. 多方向传播
同一引擎支持：
- forward：起点→终点；
- backward：终点→起点；
- bidirectional：中间锚点同时向两边；
- mixed：过程中随时因新锚点/新采用交通改变传播方向。

传播得到的“目标时间”只是路线查询条件，不是虚构的真实交通结果。

## 5. Query / Preview / Adopt
例：固定 G93 20:21，南京南最低停留40分钟：
- 计算目标到达 <= 19:41；
- 自动查询前段交通；
- 候选路线保持 Preview；
- 用户 Adopt 某路线，例如19:36到；
- 正式时间回填为19:36，停留=45分钟；
- 不把19:36伪造成19:41。

## 6. 修改时间
当前南京南：19:56到 / 20:21离 / 25分钟；20:21由G93固定。
用户改到达为19:30：
- G93不动；
- dwell 自动变51分钟；
- 原前段交通19:56到产生冲突；
- 自动查询“<=19:30到”的前段方案；
- 无歧义非班次交通可自动刷新；有具体班次/路线选择则推荐 + 用户Adopt。

## 7. 冲突求解顺序
首要原则：最小改动，不把局部冲突先扩散成全局重排。

典型顺序：
1. 检查局部交通替代是否能解决；
2. 计算额外费用/风险/时间收益；
3. 用户接受 → 只替换局部；
4. 用户拒绝 → 才向前/向后寻找其他妥协；
5. 可调整预约、活动时间也可成为候选，但必须计算后续连锁影响；
6. 多个地点可压缩时，系统生成少量具体方案，不把“缺20分钟”留给用户自己算。

## 8. 可行性 vs 体验质量
方案必须同时评估：
- feasibility：能否在时间/客观规则上成立；
- experience quality：活动/吃饭/景点被压缩后是否仍合理。

“数学上赶得上”不等于“值得推荐”。例如晚餐只剩20分钟可能是低质量解。

## 9. 推荐排序
未知用户偏好时：
1. 保住重要/受保护安排；
2. 风险更低；
3. 影响范围更小；
4. 综合额外费用；
5. 综合体验损失；
6. 再考虑总耗时等。

已知用户偏好时可动态调整排序，但不能自动采用。

## 10. 推荐展示与打扰控制
- 默认 1 推荐 + 最多2备选；
- 用户拒绝或关闭 → 同一冲突进入 quiet-assist；
- quiet-assist 只实时更新缺口/风险标识；
- 用户主动“帮我优化”才再生成；
- 风险明显升级/事实变化 → 新风险事件，可重新提醒并带新方案；
- 冲突解决后标识静默消失。

## 11. 预约与班次的差异
- 有客观截止的火车/航班/末班车：硬事实不能被用户信心抹掉；
- 餐厅等预约没有可靠迟到规则时，不假设“必须一秒不迟”，只提示非常紧张，由用户决定是否调整；
- 如果存在可靠容忍规则，按真实规则建模；
- 修改预约属于外部事实变化，必须用户确认，不能静默执行。

## 12. 缓冲
缓冲必须区分：
- mandatory
- recommended
- userPreferred

路线自身已包含的步行/换乘时间不能重复扣除。查询条件应基于“尚未包含的必要环节 + 约束”。

## 13. 开发上必须隔离的层
建议至少拆分：
- TimeGraph / ConstraintGraph
- PropagationEngine
- TransportQueryAdapter
- ConflictDetector
- CandidateGenerator
- CandidateScorer / RecommendationPolicy（可替换）
- Preview/Adopt service
- Explanation builder

核心时间传播不得直接写死推荐排序。

## 14. 第一批自动化验收案例
1. 中间固定班次反推前段交通；
2. 到达目标 vs 实际路线到达不同，保留二者；
3. 已采用班次天然锚定；
4. 修改停留导致前段冲突；
5. 修改到达导致自动查前段交通；
6. 局部打车可解决，先推荐局部；
7. 打车代价过高，改预约可能更优；
8. 改预约后晚餐只剩20分钟，不应作为高质量推荐；
9. 用户拒绝推荐后 quiet-assist；
10. quiet-assist 中风险升级，重新提醒并生成新方案；
11. 只有 recommended 无 mandatory 时不生成红色硬风险；
12. 交通查询失败不等于无车；
13. 已实际发生部分不被未来传播改写；
14. 跨日使用完整日期和当地时区；
15. Preview 不改变正式行程，Adopt 原子落地。
