## Configuration and API

Default: `PLACE_SEARCH_PROVIDER=unconfigured`. For development/test SYNTHETIC only: `PLACE_SEARCH_PROVIDER=synthetic`, `APP_ENV=development|test`, `SYNTHETIC_CI_ONLY=true`. Synthetic is rejected in staging/production. For future separately authorized real operation: `PLACE_SEARCH_PROVIDER=geoapify`, the two explicit live/storage flags and server-only key. No key goes to Web, response or error text. Fixed HTTPS host; redirect rejected; timeout; no retries. Unsupported data sources/missing required name/ID are omitted; bad or absent coordinates remain null.

- `POST /trips/:tripId/place-search` `{query, language?}`: authenticated private Trip read, validate query/language, request Provider, return candidates with Provider/external identifier, name, address, reliable coordinates or null, attribution, SYNTHETIC marker and signed owner/Trip-bound evidence. **No Place, receipt, execution, Trip, date, route or version writes.** Search does not select the first result.
- `POST /trips/:tripId/place-selection` `{selectionToken, baseTripVersion, idempotencyKey, targetDay, position, note?}`: an explicit **add-to-Trip write**, not the UI's local selection click. Verify signature, owner/Trip, expiration and coordinates. Ignore client-invented coordinates/names; build the existing ADD_PLACE_VISIT CUSTOM command from signed fields, append source/ID to the note, execute existing atomic authoring. Success increments version once and creates the usual receipt/Place/node; conflict or adjacency/date rejection rolls back everything; identical request/key replays normally while evidence remains valid.

The service creates a new private Place on explicit candidate addition; it does not merge by name or coordinates. Existing saved-place choices still reuse the exact private Place ID. External IDs are evidence on the selected arrangement/receipt, not a new global Place identity field. This intentionally does not implement cross-search deduplication. A candidate lacking coordinates can be inspected but cannot become a navigation Place; no address/name/browser-location inference occurs.

Selection is local draft state. Search input/language/cancel never creates a Place. Provider-only failure uses distinct `PLACE_SEARCH_UNAVAILABLE` and leaves note drafts/saved selection usable; core `SERVICE_UNAVAILABLE`, network and authentication errors flow through existing authoring recovery/authority concealment. Candidate-specific form values preserve submitted-snapshot dirty tracking when a different candidate is selected after saving; no automatic addition occurs. Existing authoring unknown-write replay, explicit version reload/acknowledgement and removed-date retarget remain. Search replies are fenced by picker identity and DOM connectivity; cancelled/closed/account-switched requests cannot restore candidates. On process restart or 24h expiration, re-search is needed. If evidence expires during recovery of an unknown write, the new selection-specific hook first reads current Trip authority, retains the note, clears only unusable candidate evidence and shows current arrangements with an explicit unknown-outcome warning; no write is acknowledged or automatically retried with a fresh key. The user must review before another selection/addition. There is no durable multi-instance candidate signing key or account-wide quota yet.

Maps/navigation use the selected Place's stored reliable coordinates through existing helpers. No embedded SDK, automatic authoring, geolocation, Query/Preview/Adopt, hotel guessing, recommendations, booking, photos/reviews, OCR/attachments, P6C or Google Transit work.
